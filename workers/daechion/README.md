# 프로세스2 청구 작업자

기존 register_checker의 V1 발송 endpoint·계정 필드·SHA-256 생성 방식을 재사용하는 별도 실행부다. 기존 프로그램/Sheets/문자 템플릿은 import하거나 수정하지 않는다. 상품은 홈페이지 관리자가 프로세스2로 저장하고 서버의 명시적 대치온 강의 연결을 검증해 DB에 접수한 신청만 처리한다.

2026-11-07: 운영 DB와 별도 작업자를 준비하고 --check 검수를 완료했다. 신청·관리자·수신 콜백·안내 문자·Sheets 실행부는 개발 브랜치에 구현되어 있다. 작업자는 점검 후 종료하는 상태이며 실제 청구·결제조회·대치온 등록·문자·일반 Sheets 동기화는 꺼져 있다. 운영 홈페이지에는 프로세스2를 아직 배포하지 않았다.

## 실행

실제 API 등록 검수에서 기존 영상의 파일 권한이 자동 부여되지 않았다. 전체 기본 정책을 '참여자 모두에게'로 변경한 뒤 검수 계정의 차시 등록을 새로 만들어도 같았다. 따라서 DAECHION_ACCESS_POLICY_VERIFIED 기본값은 false다. 실제 파일 접근까지 확인하기 전에는 자동 수강 등록과 준비 완료 안내 단계를 실행하지 않는다. --check와 Sheets 초기화는 이 제한과 별개다.

강의 고유 ID 사전 확인: `node scripts/daechion-api-check.cjs --lecture-id 123`. 해당 ID의 존재·진행중 상태·차시 유무·차시 ID 중복을 읽기 전용으로 확인한다. 필요하면 `--student-id 456`을 함께 사용한다. 이 명령은 학생 생성이나 등록을 하지 않는다.

1. `npm ci`
2. `npm run build:daechion-worker`
3. 전용 비공개 환경에 `env.example`의 값을 설정한다. 실제 키와 연결 문자열을 파일/Git/로그에 넣지 않는다.
4. `DAECHION_BILLING_WORKER_ENABLED=true`, `DAECHION_BILLING_SEND_ENABLED=false`로 설정한 뒤 `node workers/daechion/billing.cjs --check`로 점검한다.

`--check`는 설정과 마이그레이션 이력/테이블 읽기 검사만 수행한다. 발송 플래그가 켜져 있거나 `--once`를 함께 입력해도 청구 예약·발송·외부 결제선생 조회를 하지 않는다. 스키마가 없으면 실패하며 자동 생성하지 않는다.

이후 전체 연결 검수와 실제 발송 준비가 끝난 뒤에만 발송 플래그를 명시적으로 켠다. `--once`는 1회, 인자 없는 실행은 30초 간격으로 발송·조회·등록 단계별 최대 5개씩 처리한다. 발송 플래그가 꺼지면 청구 예약을 만들지 않는다. DAECHION_PAYMENT_READ_ENABLED와 DAECHION_ENROLLMENT_ENABLED는 조회/등록 전용 스위치이며 기본값은 모두 false다. 등록을 켜려면 결제 조회도 켜야 한다. 종료 시 현재 처리 중 요청 결과가 불명이면 아래 규칙을 따른다.

## 발송과 복구 규칙

- DB에서 신청 행을 잠근 뒤 청구서 ID를 먼저 예약한다. 새 번호는 9로 시작하는 숫자 20자리이며 DB 고유 제약도 검사한다. 기존 YYYY... 번호와 분리한다.
- 금액은 접수 당시 스냅샷이며, 수신 번호는 결제 번호다. 보호자 로그인 번호로 자동 대체하지 않는다.
- 외부 POST 전에 SEND_UNKNOWN으로 저장하고 커밋한다. 이 시점 이후 재시작/시간 초과/중복 응답/응답 저장 실패는 자동 재발송하지 않는다. 다중 작업자가 같은 신청을 읽어도 RESERVED→SEND_UNKNOWN 전이를 성공한 한 작업자만 발송한다.
- 정상 코드와 같은 청구서 번호, 제공되는 계정/해시 응답을 대조한 경우에만 SENT로 기록한다. 7일 자동 등록 대기는 이 확인 시각에서 계산한다. 발송 응답이 불명이면 임의 시각으로 대기 만료를 계산하지 않는다.
- 기존 발송 코드의 청구서 유효기간 30일은 유지한다. 7일 대기 종료를 이유로 청구서를 파기하거나 유효기간을 7일로 줄이지 않는다. 자동 환불/파기 API는 구현하지 않는다.
- SEND_UNKNOWN도 같은 청구 ID로 결제선생을 조회한다. 결제가 확인돼도 실제 발송 시각을 알 수 없으므로 관리자 확인 대상으로 남긴다. RESERVED로 되돌리거나 새 번호로 다시 발송하지 않는다. /admin/daechion 복구 화면은 구현됐으며 운영 환경 검수는 남아 있다.
- 운영 계정이 바뀌면 기존 청구를 다른 결제선생 계정으로 보내지 않고 오류를 반환한다. 수동 HOLD·다른 검토 사유는 발송 응답 도착으로 해제하지 않는다.
- 발송 완료는 결제 완료나 대치온 등록 완료가 아니다. 학생용 LMS 준비 완료 문자를 큐에 넣지 않는다.

## 결제 확인과 대치온 등록

- 등록 전 실제 API의 학생/보호자 1·2 번호 및 비활성 조회 범위를 검수하고 DAECHION_IDENTITY_LOOKUP_VERIFIED=true를 설정해야 한다. 학생/보호자 1과 비활성 사례는 확인했지만 보호자 2 사례는 남아 있어 기본값 false를 유지한다.
- 기존·신규 선택이 필수이며 학생 번호/보호자 번호를 모두 조회한다. 어느 번호든 일치하면 기존 기록이다. 선택 불일치·복수 학생·번호 역할/이름 불일치·조회 실패는 확인 필요다. 같은 신청이 생성한 계정만 DB 생성 근거로 재사용한다. 다른 신청의 409 충돌을 자동 재사용하지 않는다. 번호별 생성 확보는 결과 불명 시 유지하며 관리자 복구 전 임의 해제하지 않는다.

- V1 read의 청구 ID/계정/금액을 검증한다. 원본 응답에 있는 카드·계좌·API 키 등은 저장하지 않는다. 승인 시각은 검증한 KST 14자리/공백 날짜 형식 또는 시간대가 명시된 ISO만 해석하며, 불명확하면 수동 확인이다. 실제 운영 응답 형식 검수는 별도로 필요하다.
- 최근 검사가 끝난 토큰과 일치하는 응답만 DB에 적용한다. 늦게 도착한 예전 조회 결과가 새 결제 상태를 덮어쓰지 못하게 한다. 날짜/금액 불일치, 취소, 발송 불명, 수동 HOLD는 자동 등록하지 않는다.
- 7일 경과 후 실제 미납 W를 확인한 경우만 대기를 종료한다. 조회 장애로는 만료시키지 않는다. 기한 내 결제를 뒤늦게 발견하면 자동 만료만 복구할 수 있으며, 기한 뒤 결제와 관리자 수동 보류는 확인 대상으로 유지한다.
- 등록을 켜려면 DAECHION_API_KEY와 DAECHION_TENANT_ID를 설정한다. 실제 실행에서 /v1/me의 tenant와 일치함을 확인한 뒤 등록한다. --check는 이 외부 요청을 하지 않는다. tenant 값은 승인된 읽기 전용 검사에서 확인한 값을 넣으며 임의로 추측하지 않는다.
- 결제 확인·활성·검토 사유 없음 상태만 등록 작업을 확보한다. 같은 신청은 한 번에 한 강의만 처리한다. 만료된 등록 claim은 외부 쓰기 결과가 불명일 수 있어 REVIEW/HOLD로 남기며 자동 재시도하지 않는다.
- 학생 번호/이름과 보호자 로그인 번호를 대조한다. 결제 번호는 대치온 계정 생성에 전달하지 않는다. 비활성 계정은 재사용하며 비밀번호 초기화 API는 호출하지 않는다.
- 외부 생성/등록 직전에 결제·수동 보류·claim을 다시 확인한다. 외부 등록 도중 취소가 일어나면 완료·안내를 막고 확인 대상으로 기록한다. 두 서비스 사이의 동시 취소와 외부 POST를 원자적으로 묶을 수는 없으므로 이미 부여된 권한의 실제 회수는 사용자 결정대로 관리자 수동 처리다.
- 모든 연결 강의가 DONE일 때만 READY_MESSAGE 작업을 한 번 만든다. 안내 문자 실행부는 구현됐으며 실제 발송은 꺼져 있다. 취소 시 대기 문자는 중단하고 이미 완료한 강의의 등록 기록을 지우거나 권한 회수 API를 호출하지 않는다.

웹에는 /api/daechion/payssam/notification 수신 경로를 배포한다. web-env.example의 DAECHION_PAYSSAM_CALLBACK_ENABLED=true와 비공개 PAYSSAM_API_KEY 설정 후에만 수신 확인 응답을 제공한다. 작업자의 DAECHION_BILLING_CALLBACK_URL은 이 경로의 HTTPS 주소여야 하며 다른 경로를 거부한다. 위조/중복/잘못된 금액의 콜백으로 결제·수강 상태를 바꿀 수 없다. 결제선생의 알림에는 API 키·결제 정보가 포함되므로 프록시/APM/웹 로그에서 요청 본문을 수집하지 않는다.

## 관리자 화면을 통한 콘텐츠 권한 보완

API 등록 성공과 콘텐츠 권한 확인을 분리했다. 등록 후 `access_state=PENDING`을 기록하고 선택적인 브라우저 실행부가 세 권한 적용과 각 파일의 실제 권한을 확인한 뒤에만 `VERIFIED`로 완료한다. 미확인 상태에서는 안내를 예약하거나 발송하지 않는다. 관리자의 외부 수동 완료 기록은 `MANUAL`로 구분한다. 기존 등록 행을 자동으로 검증 완료로 바꾸지 않는다.

브라우저 실행은 `Dockerfile.browser` 이미지 및 별도 비공개 관리자 인증 연결이 필요하다. 기본 경량 이미지와 `--check` 동작은 유지한다. 실제 서버 검수 전에는 브라우저/권한 검증 플래그를 활성화하지 않는다. 자세한 인증 준비·검증 범위·보류 처리는 [콘텐츠 권한 보완](../../docs/daechion-content-access.md)을 따른다.

## 근거와 검증

## 별도 Sheets 발행

DAECHION_SHEETS_ENABLED 기본값은 false다. DAECHION_SHEETS_SPREADSHEET_ID(새 파일), DAECHION_SHEETS_SHEET_ID(숫자 탭 ID), GOOGLE_SHEET_ID(기존 파일 비교용), GOOGLE_SERVICE_ACCOUNT_JSON을 비공개 환경변수로 설정한다. 기존 파일은 쓰기 대상으로 거부한다. 사용 중인 파일에 직접 초기화하지 않는다.

빈 새 탭을 준비하고 `node workers/daechion/billing.cjs --setup-sheets`를 명시적으로 실행하면 헤더·직원 메모 열·조건부 색상을 초기화한다. 기존 데이터가 있으면 실패하며 지우지 않는다. --check는 --setup-sheets가 함께 있어도 읽기 전용 점검만 한다. 이후 일반 작업 주기에 SHEETS 작업 최대 5개를 동기화한다.

행 UUID metadata와 헤더를 검증한 뒤 관리 대상 열만 RAW/명시적 stringValue·numberValue로 기록한다. 메모 열은 보존한다. 외부 쓰기 결과가 불명인 작업은 UNKNOWN이며 같은 신청의 추가 발행을 중단한다. 이 경우 기존 행/metadata를 대조한 뒤 관리자 복구가 필요하며 임의 재삽입하지 않는다. Sheets 실패가 결제나 수강 상태를 바꾸지는 않는다.

쓰기 요청을 시작하기 전의 일시적 조회 실패(통신 오류·429·일부 5xx)만 60초 뒤 재시도한다. 한 작업에서 총 3회 시도까지 허용하고 계속 실패하면 UNKNOWN으로 남긴다. 인증/접근 권한/파일 없음 오류, 잘못된 헤더나 초기화 표식, 실제 쓰기 시작 후의 실패는 즉시 UNKNOWN이다. developerMetadata:search는 POST 형식이지만 읽기 작업이며, 그 외 POST는 요청 직전부터 쓰기 결과 불명 가능성이 있는 것으로 취급한다. 로그의 deferred는 안전하게 재시도 대기시킨 작업 수다.

실제 새 파일 생성·접근 권한·초기화와 별도 가상 탭의 정렬·번호 보존·메모 보존 검수는 완료했다. 일반 동기화와 웹 접수는 아직 비활성이다. 웹 설정은 web-env.example을 따른다.

현재 운영 소스 apply_checker.py의 send_bill 구현과 대조했다. 공식 V1 명세도 확인했다.

- https://developers.payssam.kr/api/api-v1/send.md
- https://developers.payssam.kr/api/api-v1/bill.md

공식 문서상 신규 연동은 V2 권장이지만, 이번 범위는 사용자가 요청한 기존 운영 V1 연동 유지다. 키/프로토콜을 임의로 V2로 교체하지 않는다.

`npm run test:daechion`은 모의 공급자와 격리 DB만 사용한다. GitHub는 별도 PostgreSQL에서 동시 발송 claim과 실제 작업자의 읽기 전용 `--check`까지 검사한다. 그 후 기존 홈페이지 전체 빌드와 HTTP 회귀 검사를 실행한다. 실제 상품/학생/청구서/문자/운영 DB는 이 검사에 사용하지 않는다.
