# 프로세스2 청구 작업자

기존 register_checker의 V1 발송 endpoint·계정 필드·SHA-256 생성 방식을 재사용하는 별도 실행부다. 기존 프로그램/Sheets/문자 템플릿은 import하거나 수정하지 않는다. 상품은 홈페이지 관리자가 프로세스2로 저장하고 서버의 명시적 대치온 강의 연결을 검증해 DB에 접수한 신청만 처리한다.

현재 개발 브랜치 전용이며 운영 작업자를 생성/시작하지 않았다. 공개 접수·콜백/결제 조회·수강 등록·관리자 복구 화면·Sheets 발행은 아직 연결 중이다. 이 단계의 코드만으로 실제 발송을 활성화하지 않는다.

## 실행

1. `npm ci`
2. `npm run build:daechion-worker`
3. 전용 비공개 환경에 `env.example`의 값을 설정한다. 실제 키와 연결 문자열을 파일/Git/로그에 넣지 않는다.
4. `DAECHION_BILLING_WORKER_ENABLED=true`, `DAECHION_BILLING_SEND_ENABLED=false`로 설정한 뒤 `node workers/daechion/billing.cjs --check`로 점검한다.

`--check`는 설정과 마이그레이션 이력/테이블 읽기 검사만 수행한다. 발송 플래그가 켜져 있거나 `--once`를 함께 입력해도 청구 예약·발송·외부 결제선생 조회를 하지 않는다. 스키마가 없으면 실패하며 자동 생성하지 않는다.

이후 전체 연결 검수와 실제 발송 준비가 끝난 뒤에만 발송 플래그를 명시적으로 켠다. `--once`는 1회, 인자 없는 실행은 30초 간격으로 최대 5개씩 처리한다. 발송 플래그가 꺼지면 청구 예약을 만들지 않는다. 두 플래그는 기본값이 모두 false다. 종료 시 현재 처리 중 요청 결과가 불명이면 아래 규칙을 따른다.

## 발송과 복구 규칙

- DB에서 신청 행을 잠근 뒤 청구서 ID를 먼저 예약한다. 새 번호는 9로 시작하는 숫자 20자리이며 DB 고유 제약도 검사한다. 기존 YYYY... 번호와 분리한다.
- 금액은 접수 당시 스냅샷이며, 수신 번호는 결제 번호다. 보호자 로그인 번호로 자동 대체하지 않는다.
- 외부 POST 전에 SEND_UNKNOWN으로 저장하고 커밋한다. 이 시점 이후 재시작/시간 초과/중복 응답/응답 저장 실패는 자동 재발송하지 않는다. 다중 작업자가 같은 신청을 읽어도 RESERVED→SEND_UNKNOWN 전이를 성공한 한 작업자만 발송한다.
- 정상 코드와 같은 청구서 번호, 제공되는 계정/해시 응답을 대조한 경우에만 SENT로 기록한다. 7일 자동 등록 대기는 이 확인 시각에서 계산한다. 발송 응답이 불명이면 임의 시각으로 대기 만료를 계산하지 않는다.
- 기존 발송 코드의 청구서 유효기간 30일은 유지한다. 7일 대기 종료를 이유로 청구서를 파기하거나 유효기간을 7일로 줄이지 않는다. 자동 환불/파기 API는 구현하지 않는다.
- SEND_UNKNOWN은 같은 청구 ID로 결제선생 조회/관리자 확인을 거쳐 복구해야 한다. RESERVED로 되돌리거나 새 번호로 다시 발송하지 않는다. 실제 조회 결과와 관리자 복구 동작은 다음 연결 단계이며, 현 단계에서 자동 해제하지 않는다.
- 운영 계정이 바뀌면 기존 청구를 다른 결제선생 계정으로 보내지 않고 오류를 반환한다. 수동 HOLD·다른 검토 사유는 발송 응답 도착으로 해제하지 않는다.
- 발송 완료는 결제 완료나 대치온 등록 완료가 아니다. 학생용 LMS 준비 완료 문자를 큐에 넣지 않는다.

## 근거와 검증

현재 운영 소스 apply_checker.py의 send_bill 구현과 대조했다. 공식 V1 명세도 확인했다.

- https://developers.payssam.kr/api/api-v1/send.md
- https://developers.payssam.kr/api/api-v1/bill.md

공식 문서상 신규 연동은 V2 권장이지만, 이번 범위는 사용자가 요청한 기존 운영 V1 연동 유지다. 키/프로토콜을 임의로 V2로 교체하지 않는다.

`npm run test:daechion`은 모의 공급자와 격리 DB만 사용한다. GitHub는 별도 PostgreSQL에서 동시 발송 claim과 실제 작업자의 읽기 전용 `--check`까지 검사한다. 그 후 기존 홈페이지 전체 빌드와 HTTP 회귀 검사를 실행한다. 실제 상품/학생/청구서/문자/운영 DB는 이 검사에 사용하지 않는다.
