# 신규 강의 전용 결제 작업자

기존 register_checker 서비스와 별도로 배포한다. 기존 main.py·Google Sheets·학생 파일을 읽거나 수정하지 않는다. Python 표준 라이브러리만 사용하며 PostgreSQL에 직접 접속하지 않는다. 홈페이지 내부 작업 API를 인증해 작업을 가져오고 결과를 보고한다.

## Railway 설정

1. 신규 worker 서비스를 만든다. 이 저장소의 `workers/lectures`를 Root Directory로 사용한다. 이 폴더의 Dockerfile이 worker.py를 실행한다. 기존 홈페이지/기존 register_checker 서비스의 Root Directory나 시작 명령을 변경하지 않는다.
2. env.example에 있는 항목을 새 서비스 환경변수에 설정한다. 기존 결제선생의 PAYSSAM_API_KEY/MEMBER/MERCHANT는 worker에만 설정한다. 실제 값을 Git/채팅/로그에 넣지 않는다.
3. LECTURES_WEB_ORIGIN은 홈페이지 HTTPS Origin이다. 내부 API는 LECTURES_WORKER_TOKEN으로 인증한다. 홈페이지 서비스에도 동일한 토큰과 LECTURES_WORKER_ENABLED=true가 필요하다. 토큰은 충분히 긴 무작위 값(최소 32자)을 사용한다.
4. 처음에는 LECTURES_WORKER_SEND_ENABLED=false로 두고 서비스와 API 연결부터 확인한다. LECTURES_WORKER_ENABLED가 true가 아니면 worker는 요청 없이 종료한다.
5. 실제 발송은 운영 환경과 지정한 검수 대상을 확인한 뒤 SEND_ENABLED=true로 활성화한다. 신규 환경은 기본 비활성으로 시작한다. 2026-11-04 별도 Railway 검증 환경에서 사용자 승인에 따른 1,200원 단건 발송·실결제·자동 강의 오픈을 확인했다. 이후 SEND_ENABLED=false로 되돌리고 조회 전용으로 실행 중이다. 검증 성공을 운영 홈페이지 전체 발송 승인으로 해석하지 않는다.

로컬 실행 명령: `python workers/lectures/worker.py --once`. 기본 비활성 상태에서는 네트워크 요청을 하지 않는다. 실제 변수는 OS 환경변수를 읽으며 env.example 파일을 자동으로 읽지 않는다.

## 청구 작업 없는 연결 점검

웹 코드 배포와 변수 설정 후 `python workers/lectures/worker.py --check`를 먼저 실행한다. Docker 이미지에서는 시작 명령을 `python -u worker.py --check`로 지정할 수 있다. 성공하면 종료 코드 0, 비활성·인증 실패·연결/스키마 오류면 0 이외로 종료한다. 한 번만 실행하는 점검 명령이므로 점검 서비스는 자동 재시작하지 않도록 설정한다.

이 명령은 인증된 `POST /api/lectures/internal/billing/health`에 빈 JSON만 보낸다. DB 연결과 청구 테이블의 필요한 열을 읽기 전용으로 확인하고, 주문·lease·발송 요청은 변경하지 않는다. SEND_ENABLED=true여도 청구 작업을 가져오거나 결제선생에 발송·조회하지 않는다. 실제 계정 키의 유효성이나 결제선생 연결 성공까지 확인하는 명령은 아니다. 점검만 할 때도 SEND_ENABLED=false를 유지한다.

검증 사이트의 기존 가상 주문은 실제 수신자가 아닌 시험용 번호로 만들어졌으므로 실제 발송을 활성화하기 전에 대기 요청을 확인한다. 기존 수강생용 register_checker는 수정하거나 중지하지 않는다.

## 처리 규칙

- SEND는 서버가 발급한 고정 청구 ID·수신자·서버 금액을 사용한다. 성공 여부가 불명확하면 UNKNOWN으로 보고하고 절대로 자동 재발송하지 않는다.
- 청구 ID는 L로 시작하는 20자리다. V1 발송 명세의 문자/숫자 최대 20자리 규칙에 맞추고 기존 시트의 숫자/S 계열과 분리했다.
- V1 `/if/bill/send`의 기존 필드와 SHA-256(bill_id,phone,price)을 사용한다. 성공 코드와 응답 ID를 확인하고, 응답에 계정/hash가 있으면 대조한다.
- V1 `/if/bill/read`의 appr_state F/W/C/D를 정규화한다. 실제 기존 단건 검증에서 code 필드가 없었으므로 code 부재 자체를 오류로 처리하지 않는다. ID와 F의 정수 금액은 반드시 검증한다.
- 외부 호출은 15초 제한, redirect 차단. 응답 원문과 API 키는 저장/로그 출력하지 않는다. 결과 보고 실패만 같은 작업 토큰·같은 본문으로 최대 3회 시도한다. 외부 발송 자체는 재시도하지 않는다.
- 매 사이클 SEND/READ 각각 최대 5건, 사이클 간 10초 대기다. 서버가 조회 대상 시점을 관리한다. 통상 미납 30초, 완료 30분, 확인 필요 5분 후 재조회 목표이며 처리량/장애로 지연될 수 있다. 실제 공급자 호출 한도와 운영 건수에 맞춘 검증이 필요하다.
- 기존 프로그램과 공급자 계정/호출량은 공유할 수 있다. 서비스 분리가 공급자 한도까지 분리하는 것은 아니다.

## 만료·취소·콜백

확인된 발송 시각부터 홈페이지 기한은 168시간이다. V1 expire_dt는 날짜 단위이므로 worker는 한국 날짜 기준 7일 뒤 날짜를 넣는다. 외부 종료 시각이 홈페이지 기한과 정확히 같다고 보장하지 않는다. 기한 경과 W/조회 오류는 관리자 확인 대상으로 남기고, 기한이 지났으며 D로 확인된 미납 주문만 자동 EXPIRED로 처리한다. 파기·취소·환불 API는 이 worker에서 호출하지 않는다.

취소 C는 권한을 회수하지 않고 검토 대상으로 남긴다. 미해결 취소는 다음 F가 와도 검토 표시가 유지된다. 관리자가 직접 확인해 오픈/회수하면 이전 검토를 처리한 것으로 기록하며, 새 조회가 다시 다르면 새로 표시한다. 이미 PAID인 주문은 W/D로 자동 되돌리지 않는다.

PAYSSAM_CALLBACK_URL을 생략하면 홈페이지의 `/api/lectures/payssam/notification`을 사용한다. 이 URL은 수신 확인만 응답하고 콜백 본문을 신뢰하거나 DB·권한을 변경하지 않는다. 자동 확인의 유일한 외부 근거는 인증된 worker의 서버 조회다. 콜백 응답을 결제 승인/DB 반영 완료로 해석하지 않는다.

## 운영 전 확인

실제 PostgreSQL 다중 연결·두 worker의 동시 claim, Railway 네트워크/TLS, 작업자 재시작, 실제 공급자 발송/응답, 고객 안내를 검증해야 한다. 지금까지의 단위/PGlite 검사는 이를 대신하지 않는다. 실청구 전 테스트 대상과 금액을 확인하고 기존 운영 시트에는 테스트 행을 넣지 않는다.

명세 근거: [결제선생 V1 발송·파기 공식 문서](https://developers.payssam.kr/api/api-v1/send). 기존 V1 조회 실검증 결과는 별도 프로젝트 보고서에 보존했다.

## 관리자 재조회와 복귀

034 이후 서버는 관리자 재조회 요청을 우선 배정한다. 요청 전에 이미 시작한 조회는 다음 요청의 완료로 간주하지 않는다. 이 기능은 worker의 전송 형식을 바꾸지 않으며 순서 추적은 웹 DB에서 처리한다. 자동 처리 복귀는 관리자 화면에서 최신 F/금액/ID·현재 주문 버전·조회 대기 여부를 확인한 뒤 명시적으로 수행한다. worker는 수동 결정을 스스로 해제하지 않는다.
