# 일괄 결제·묶음상품 구현 계약 1단계

사용자 확정 기준은 2026-11-08 설계 v2.2와 중복 결제 경고 추가 사항이다. 태그/검색 확장, 개수별 할인, 할인율 입력, 자체 회원/강의실은 추가하지 않는다.

## 이번 브랜치의 범위

`lib/daechion/orders/cart.ts`에 서버 상품 해석·정확한 합계·구성 ID 중복·신뢰된 보유 권한 결과 판정을 구현했다. `db/daechion-orders/001_initial.sql`은 새 주문 원장의 초기 DDL이다. 기존 `daechion_automation` 마이그레이션 목록에 등록하지 않았으며 운영 DB에 적용하지 않았다.

HTTP 세 경로의 기본 비활성 구현과 견적/주문 저장 서비스를 추가했다. 관리자 화면의 묶음상품 생성·수정 및 학생 장바구니를 연결했다. 합산 청구·결제 조회·다중 강의 작업자, 신규 주문용 Sheets 게시·완료 안내 전송 계층과 지정 주문 한 건용 실행부를 구현했다. 실제 운영 작업자의 시작 명령은 변경하지 않았다. 새 스키마를 운영 DB에 적용하거나 공개 접수를 활성화하지 않았다.

## 관리자 상품 계약

- 기존 `/admin/classes`의 수업 추가 옆에 묶음상품 추가를 두었다. 목록에 묶음상품 및 연결 강의 개수를 표시하고 같은 편집 화면에서 수정한다.
- 묶음 생성은 `saleKind=BUNDLE`, `purchaseProcess=PROCESS_2`로 고정한다. 구성은 대치온 고유 ID 두 개 이상이고 같은 ID를 중복 저장할 수 없다.
- 개별 신규 상품은 `saleKind=SINGLE`이며 연결 ID 하나가 기본이다. 기존 다중 연결 상품은 이름/구성 수만 보고 자동 재분류하지 않는다. 새 주문에 편입하려면 관리자 확인이 필요하다.
- 묶음 최종 판매가는 원 단위 양의 정수다. 구성 강의 가격을 다시 더하거나 별도 교재비를 덧붙이지 않는다. 개별 상품의 현재 교재비가 있으면 서버 어댑터에서 표시/동의된 총 판매가로 정규화한다.
- 묶음상품 편집은 프로세스2·온라인으로 고정하고 최종 판매가만 받는다. 별도 교재비·개수별 가격·기존 Sheets 신청 라벨은 표시하지 않는다. 기존 수업↔묶음상품 유형 변경은 금지한다. 기존 다중 연결 수업을 묶음으로 자동 전환하지 않는다.
- 현재 단계에서는 서버도 묶음의 공개 저장을 거부한다. 장바구니·금융 작업자·운영 검수를 완료한 뒤 이 차단을 해제해야 한다. 기존 단건 접수도 묶음상품을 거부하므로 준비 중 묶음이 기존 경로로 청구되지 않는다.
- 묶음 수정에는 마지막 조회의 updatedAt을 함께 보내며, 다른 편집 이후의 오래된 저장은 409로 거부한다. 이미지 업로드가 갱신한 updatedAt도 편집 화면에 반영한다.
- 최종 카탈로그 어댑터는 `productId, title, saleKind, purchaseProcess, visible, priceWon, tenantId, revision, lectures[{id,name}]`을 만든다. 브라우저가 이 값을 원본으로 보내지 못한다.
- 공개/프로세스/테넌트/고유 ID/가격 검증을 통과한 상품만 새 주문으로 판매한다. 기존 두 상품 ID는 신규 원장에서 거부한다.

## 결제 전 API 계약

| 예정 경로 | 사용자 요청 | 서버 응답/제약 |
|---|---|---|
| POST `/api/daechion/orders/cart` | `items:[{productId}]` | 서버 가격·상품명·합계·구성 중복. 중복은 실제 상품/강의 ID와 선택 상품명으로 안내 |
| POST `/api/daechion/orders/quotes` | 상품 ID 목록, 학생/보호자/청구 정보, 기존·신규 선택, 동의, 마지막 확인 금액 | 읽기 전용 학생/보유 권한 판정 후 READY/RECONFIRM/REVIEW/NO_PURCHASE. 임시 견적 토큰과 기한 |
| POST `/api/daechion/orders` | 견적 ID·비공개 견적 토큰·재전송 키·최종 확인 금액 | 원장 생성만 수행. RECEIVED는 발송/결제/수강 완료가 아님 |
| 관리자 주문 목록/조치 | 기존 관리자 인증 | 보류·수동 확인·결과 불명 확인 이력. 일반 공개 경로가 권한/금액을 강제로 수정하지 못함 |

GET `/api/daechion/orders/catalog`은 기본 비활성이고 공개 가능한 상품의 ID·이름·종류·판매가·구성 강의 개수만 응답한다. 숨김·프로세스1·설정 오류·테넌트 불일치·모호한 상품 ID는 구매 목록에 포함하지 않는다. DB 준비가 확인되지 않으면 목록을 판매 가능한 것으로 표시하지 않는다.

## 학생 장바구니 화면

`/classes/cart`에서 여러 상품을 선택하고 서버의 가격·구성 확인을 받는다. 수업 목록에는 새 접수가 사용 가능한 경우에만 ‘여러 강의 함께 구매하기’ 링크를 표시한다. 기존 카드와 기존 신청 경로는 교체하지 않는다. 새 접수 스위치를 운영에서 변경하지 않았으므로 현재는 링크가 나타나지 않는다.

구성이 겹치면 선택한 상품명과 겹치는 강의명을 표시하고 신청을 차단한다. 제외 버튼은 사용자가 직접 선택하며 가격을 자동으로 차감하지 않는다. 선택 변경 시 이전 견적과 최종 동의를 지우고 다시 확인한다. 진행 중이던 구성 확인 응답이 뒤늦게 도착해 새 선택을 덮어쓰지 못하도록 요청을 취소한다.

학생·보호자·결제 전화번호, 기존 수강 여부와 동의를 받은 뒤 서버 견적을 요청한다. 기보유 개별 제외 시 변경된 구성과 금액을 다시 확인한다. 기보유 포함 묶음·불명확 식별은 ‘담당자 확인 요청’으로 표시한다. 견적은 최종 확인 체크 전 접수하지 않으며 만료 후 다시 검증한다. 원 단위 금액을 그대로 표시한다.

주문 저장 응답이 불명확하면 새 주문을 만들지 않고 같은 견적 토큰·요청 키로 재확인한다. 이 재확인 정보만 탭의 sessionStorage에 보관하고 이름·전화번호·입력 동의 자료는 브라우저 저장소에 보관하지 않는다. 성공 후 저장된 재확인 정보를 제거한다. 복구 중에는 상품 선택·새 신청 화면을 감추고 같은 접수 확인만 제공한다. RECEIVED는 결제나 수강 등록 완료로 표시하지 않는다.

합성 데이터 로컬 검수에서 중복 차단, 기보유 개별 제외/합계 재확인, 기보유 포함 묶음의 고정가 보류, 응답 누락 후 새로고침·재확인을 확인했다. 결과는 주문 1건·청구 0건이다. 실제 기존 학생 권한 조회는 여전히 미연결이며 실환경에서는 UNKNOWN/REVIEW를 유지한다.

가격·수량·할인율·대치온 ID·결제/보유 상태를 공개 장바구니 요청에 끼워 넣으면 거부한다. 같은 판매 상품 ID도 두 번 요청할 수 없다. 초기는 상품/전체 대상 강의 각 30개로 서버 요청을 제한하며, 넘으면 부분 판매하지 않고 오류로 안내한다. 이 한도는 검증 부담을 제한하는 구현 값이며 몰래 상품을 잘라 처리하지 않는다.

장바구니에 구성 ID 중복이 있으면 HTTP 409에 대응하는 충돌 상태로 표시하고, 상품을 제거할 때까지 견적/청구를 진행하지 않는다. 이름이 같아도 ID가 다르면 충돌이 아니다. 브라우저 버튼 비활성화만으로 보호하지 않고 서버에서 다시 검사한다.

견적 시 호출할 포트는 조회만 허용한다. 계정 생성/학생 수정/수강 등록/권한 변경 함수를 호출하지 않는다. 공식 API의 테넌트·학생 전화번호 조회를 연결했다. 현재 공식 API로 기존 콘텐츠 보유 여부를 증명할 수 없으므로 기존 학생은 UNKNOWN/REVIEW로 보류한다. 신규 선언과 전화번호 조회가 모두 신규인 경우에만 NOT_OWNED로 판정한다. 이름만으로 학생을 선택하지 않으며 보호자2 번호도 조회 결과에 포함해 검사한다. `reviewOwnership`의 입력은 공개 요청이 아니라 서버 포트가 만든 결과다. 기보유 개별 제외와 묶음 보류 정책은 검증됐지만, 실제 기존 학생의 기보유 개별 제외를 자동화하려면 추가 읽기 전용 권한 조회 연결이 필요하다.

조회 결과에는 장바구니 fingerprint, 서버가 만든 subjectKey, 확인시각, 학생 식별 판정, 요청한 전체 강의 ID의 OWNED/NOT_OWNED/UNKNOWN이 포함된다. 빠진/추가/중복 ID, 다른 학생·다른 장바구니 결과, 미래 시각 또는 60초 넘은 결과는 거부한다. subjectKey는 서버 비밀키를 이용해 정규화된 입력에 바인딩하는 방향으로 연결하며, 비회원 구매자의 전화번호 소유 인증을 대신한다고 설명하지 않는다. 전체 학생 정보나 전체 보유 강의 목록은 공개하지 않는다.

### 보유 권한 판정

| 조건 | 판정 |
|---|---|
| 개별 기보유 | 해당 상품 제외, 합계 재계산, RECONFIRM |
| 전부 개별 기보유 | NO_PURCHASE, 청구/등록 없음 |
| 묶음 구성 중 하나 이상 기보유 | REVIEW, 묶음 최종 가격 그대로 보존, 자동 차감 없음 |
| 식별 보류/권한 UNKNOWN | REVIEW, 추정으로 결제하지 않음 |
| 모두 확정·미보유 | READY |

RECONFIRM도 곧바로 발송을 뜻하지 않는다. 학생이 바뀐 상품과 합계를 다시 확인해야 한다. REVIEW인 장바구니를 금액 일부만 임의로 청구하지 않는다. 학생이 묶음을 제거하면 남은 구성으로 새 검증을 시작할 수 있다.

## DB 원장과 무결성

같은 PostgreSQL의 별도 `daechion_orders` 영역을 사용한다. 기존 학생·상품 파일·단일 신청·인증 유지 테이블은 수정하지 않는다.

| 테이블 | 책임 |
|---|---|
| quotes | 임시 토큰 해시, 장바구니/학생 바인딩, 서버 스냅샷, 금액, READY/REVIEW/CONSUMED/EXPIRED, 10분 기한 |
| orders | 견적 1개당 주문 1개, 재전송 키, 학생 연락처 스냅샷, 합계, 결제/학생 식별/안내 상태 |
| items | 판매 상품별 스냅샷과 최종 가격. 묶음 가격은 여기 한 번만 기록 |
| grants | `(order_id,lecture_id)` 유일, 상품 행 연결, 독립 처리/검증 상태·실행 확보 |
| bills | 주문 금액과 복합 FK로 대조, 공급자/청구 번호 유일, 주문별 현재 청구 1개 |
| phone_claims | 학생 생성 결과 불명/동시 주문에서 중복 생성을 막는 번호 확보 기록 |
| jobs | 주문별 Sheets/완료 안내의 확보·결과 불명 상태 |
| events | 고정 이벤트 코드 이력. 원본 공급자 오류/인증 자료를 넣지 않음 |

초기 주문은 DRAFT로만 넣는다. 한 트랜잭션에서 상품과 대상 강의를 모두 넣은 후 READY로 바꾼다. DB가 견적 상태/만료/바인딩/스냅샷/상품 합계/구성 ID를 대조한 뒤 견적을 소비한다. READY를 직접 삽입하거나 REVIEW를 거쳐 검증을 건너뛰는 것도 막는다.

READY 이후에는 상품·금액·연락처·구성 ID를 바꾸거나 DRAFT로 되돌릴 수 없다. 학생이 확정된 뒤 다른 학생 ID로 바꾸는 것도 막는다. 잘못된 주문은 이력을 남기고 기존 확정 스냅샷과 구분해 처리한다.

청구는 READY 주문에서 RESERVED로만 시작하고, 예약한 청구 번호/계정/금액은 바꾸지 않는다. 실제 공급자 조회가 검증한 기록을 저장한 뒤 주문을 PAID로 바꾸는 순서다. DB의 PAID 표시는 실제 외부 승인을 대신하지 않으므로 호출 측의 청구 번호·금액·시간·공급자 검증도 필요하다.

권한 작업은 주문 PAID, 학생 식별 PASSED, 현재 청구 SENT/PAID를 갖추기 전 RUNNING/VERIFIED/MANUAL로 전환할 수 없다. 외부 쓰기 바로 직전에도 다시 확보 토큰·결제·보류를 대조하는 작업자 검증은 후속 구현에서 연결해야 한다. DB 제약만으로 외부 API 호출을 통제했다고 간주하지 않는다.

## 재전송·동시 처리와 후속 구현의 순서

1. 요청의 원본 정보로 fingerprint를 계산하고 동일 재전송 키/동일 내용은 기존 주문을 반환한다. 내용이 다르면 409로 거부한다.
2. 견적을 잠근 상태에서 토큰 해시·주체 바인딩·최종 확인 금액을 검사한다. 새 주문은 기한 안의 READY 견적만 사용한다. 기존 주문의 정당한 재조회/재전송과 새 주문 생성을 구분한다.
3. 학생/강의 ID별 진행 중 주문 충돌을 잠금과 원장으로 확인한다. 서로 다른 탭에서 토큰/요청 키만 바꿔 중복 청구하지 못하게 한다.
4. 원장/상품/대상/이벤트/Sheets 작업만 원자적으로 저장한다. DB 트랜잭션 안에서 청구 발송·등록·문자를 실행하지 않는다.
5. 작업자가 청구 확보 → 외부 발송 → 확인된 결과 기록을 수행한다. 불명확한 쓰기를 일반 재시도하지 않는다.
6. 이전 원장과 새 원장에서 같은 공급자/청구 번호가 발견되면 처리 대상을 추정하지 않고 보류한다. 기존 금융 루프와 신규 주문 루프의 활성화 범위를 분리한다.
7. 합산 결제 후 대상 강의별 작업을 수행한다. 독립적인 한 강의 실패는 완료된 다른 권한을 다시 만들지 않는다. 학생/결제 문제는 전체 주문을 보류한다.
8. 전체 권한 검증 후에만 학생/연결 보호자 안내 작업을 생성한다. 수신 번호별 수신 기록·결과 불명 보호와 관리자 조치 원장은 후속 구현에 포함한다.

## 배포 경계와 남은 작업

### 주문 작업자 코어

`billing.ts`, `enrollment.ts`, `runner.ts`, `worker-store.ts`와 별도 `002_workers.sql`을 추가했다. 기존 단건 작업자는 이 모듈을 호출하지 않는다. 새 코어는 주입한 서버 포트와 명시적 활성화 값으로만 실행하며 운영 환경변수·인증·작업자 시작 명령은 변경하지 않았다.

- 청구 전 신선한 읽기 전용 사전 검증 포트가 필수다. 합계·연락처·상품 스냅샷을 고정하고 한 주문에 청구 한 건만 예약한다. 외부 발송 전에 SEND_UNKNOWN을 저장하고, 결과 불명/충돌/저장 불명일 때 재발송하지 않는다. 기존 원장과 청구 번호가 충돌하면 보류한다.
- 동일 공급자 계정·청구 번호·금액·승인 시각을 검사한다. 조회 결과는 동시 실행 토큰으로 대조해 오래된 결과가 취소를 덮어쓰지 못한다. 미납 7일 종료와 기한 이후 결제는 구분하며, 승인 시각이 기한 안인데 늦게 발견된 결제는 검증 후 복구한다. 결과 불명 조회만으로 미납 만료를 추정하지 않는다.
- 현재 결제 조회가 성공한 경우에만 강의 처리를 호출하고, 각 강의 사이에도 결제를 다시 조회한다. DB의 유효 결제 근거는 3분 이내의 확인된 현재 청구다. 정지/취소 후에는 새로운 권한 쓰기를 차단한다. 이미 검증된 강의는 삭제하지 않으며 환불 후 회수는 수동 정책을 유지한다.
- 학생·보호자 번호를 확보하고 계정 생성 시도 사실을 먼저 저장한다. 생성 결과 불명은 재생성하지 않고 보류하며 번호 확보를 유지한다. 학생 생성/등록/권한 적용 바로 전에 결제와 확보 상태를 재검사한다. 기존 선언과 조회가 다르거나 학생 정보가 바뀌면 주문 전체를 보류한다.
- 강의별 API 등록 성공과 실제 영상·자료 권한 검증을 별도로 저장한다. 한 강의 실패는 해당 강의만 REVIEW로 남기고 다른 미처리 강의는 계속 처리할 수 있다. 검증 완료 강의는 재등록하지 않는다. API 등록 성공이 저장된 강의만 관리자 인증과 수정 버전을 검증해 권한 재확인을 대기시킬 수 있다. 등록 자체가 결과 불명인 경우에는 이 경로로 재시도하지 않는다. 이 조치는 별도 일괄 주문 관리자 화면에 연결했다.
- 모든 구성 강의의 권한이 검증돼야 완료 안내 작업을 원장에 한 번 기록한다. 이는 문자 전송 완료가 아니다. 이벤트마다 신규 주문용 Sheets 작업도 기록한다. 이 작업을 소비하는 별도 게시/안내 계층은 아래와 같다.

`DAECHION_ORDER_WORKER_ENABLED` 및 `DAECHION_ORDER_SEND_ENABLED`·`DAECHION_ORDER_PAYMENT_READ_ENABLED`·`DAECHION_ORDER_ENROLLMENT_ENABLED`는 모두 명시적 true만 허용한다. 기존 단건 발송/등록 쓰기 스위치와 동시에 켜면 설정을 거부한다. 현재 운영에서 이 새 설정을 추가하거나 활성화하지 않았다. 향후 실행부는 이 설정 함수를 거쳐야 하며 테스트 포트의 READY 사전 검증을 실환경의 조회 근거 대신 사용해서는 안 된다.

`DAECHION_ORDERS_ENABLED=true`와 전용 `DAECHION_ORDERS_SUBJECT_SECRET`(32자 이상), DB/API/테넌트/허용 Origin이 모두 설정돼야 새 HTTP 경로를 사용할 수 있다. 기존 단건 프로세스2 접수인 `DAECHION_INTAKE_ENABLED=true`와 동시에 활성화하면 새 경로는 503으로 거부한다. 프로세스1은 이 두 스위치와 무관하게 유지한다. 운영 변수는 변경하지 않았다.

견적 토큰은 응답에만 전달하고 SHA-256 해시만 DB에 저장한다. 학생·보호자·청구 입력을 서버 비밀키 HMAC에 바인딩하고, 요청 키 재전송은 견적 토큰이 맞는 경우에만 기존 접수를 반환한다. 가격/구성/공개 상태가 바뀌면 새 견적을 요구한다. 새 주문끼리는 학생·보호자 번호를 정렬해 잠근 후 대상 ID 중복을 검사한다. 과거 단건 신청 원장에도 같은 번호·강의의 진행 중/기결제 기록이 있으면 보류한다. 기존 단건 경로가 동시에 새 접수를 생성하는 경합은 활성화 스위치의 상호 배제로 차단해야 하므로 이 조건을 제거하지 않는다.

견적은 학생 번호당 15분 동안 10개로 제한한다. 이 제한은 저장량 보호이며 전화번호 소유 인증을 의미하지 않는다. 공개 전에는 조회 API 남용을 제한하는 별도 요청 제한과 운영 보관 정책도 연결해야 한다.

주문 저장은 트랜잭션 안에서 상품/대상/이벤트/Sheets 작업까지 함께 기록하며 외부 청구/등록/문자를 호출하지 않는다. REVIEW 견적은 REVIEW 주문으로만 저장한다. 변경된 합계의 RECONFIRM 견적은 응답의 새 합계를 확인한 뒤 접수해야 한다. RECEIVED는 아직 발송·결제 완료를 뜻하지 않는다.

### 신규 주문용 Sheets·완료 안내 계층

`003_delivery.sql`에 수신 번호별 안내 기록과 작업 오류 코드를 추가했다. `ready-message.ts`, `sheets-view.ts`, `sheets-publisher.ts`, `sheets-worker.ts`, `delivery.ts`는 새 원장 전용이며 기존 단건 메시지/시트 실행부는 교체하지 않았다.

완료 안내는 현재 결제를 다시 조회하고 모든 강의의 영상·자료 권한을 확인한 주문만 처리한다. 학생 번호와 등록한 보호자 로그인 번호를 중복 없이 대상으로 하며, 결제 수신 번호만 입력한 사람에게 LMS 로그인 안내를 보내지 않는다. 기존 계정은 기존 비밀번호, 신규 계정은 로그인 번호 끝 4자리를 안내하고 노션·학생카드·디스코드 절차는 포함하지 않는다. 번호별 전송 직전에 UNKNOWN을 먼저 저장한다. 응답/저장이 불명확하면 동일 번호를 자동 재전송하지 않는다. 이미 접수된 번호의 결과는 유지한다. 시도한 적 없는 안내가 일시적인 결제 조회 오류로 중단된 경우만 검증 후 재개한다. 안내의 SENT 표시는 통신사 최종 수신이 아니라 공급자 발송 접수 확인이다.

Sheets에는 주문번호, 신청시각, 입력한 학생/학부모 이름과 학생·보호자 로그인·결제 번호, 기존·신규 선택, 상품별 이름/ID/종류/판매가, 총액·동의·견적번호, 청구 번호/이력/시각/기한, 결제/학생/강의별 권한/수신 번호별 안내 상태, 중복 확인·처리 확인·사유·기준 버전·반영 시각을 표시한다. 중복 확인 통과는 초록색, 중복/처리 확인 필요는 빨간색이다. 정상적인 7일 미납 종료는 오류 대신 ‘대기 종료’로 표시한다. 과거 신원 확인이 통과했어도 현재 번호 대조 오류가 있으면 통과로 표시하지 않는다.

대상은 기존 홈페이지의 원본 Sheets 파일과 달라야 하며, 기존 단건 프로세스2 탭과도 달라야 한다. 새 전용 파일 또는 기존 신규 업무 파일의 별도 빈 탭을 명시적으로 초기화한다. 기존 탭의 헤더를 확장하거나 행을 섞지 않는다. 새 탭 전용 표식과 주문번호 행 메타데이터로만 게시하며, 직원 메모 열은 보존하고 입력값/청구 번호는 문자 그대로 기록한다. 헤더·행 표식·주문번호가 맞지 않으면 쓰기를 멈춘다. 행 삽입 시에도 새 행의 빨강/초록 규칙이 유지되도록 조건부 서식은 헤더를 포함한 열 범위에 적용한다.

한 주문의 동기화를 확보한 뒤 최신 버전을 투영하고, 그동안 추가된 이후 버전 작업은 남겨 다음 반영으로 처리한다. 쓰기 결과 불명은 UNKNOWN으로 보존해 중복 행 삽입을 막는다. 서버 내부 승인 포트를 통과한 복구는 기존 행이 확인된 경우에만 갱신하며, 행이 없으면 새로 삽입하지 않는다. 시트 읽기만 실패하고 쓰기가 없었던 경우에는 제한된 지연 재시도를 허용한다. 이 복구 조치는 아직 관리자 화면에 연결하지 않았다.

Sheets API 자체가 끊기거나 헤더가 손상되면 그 장애를 같은 시트에 즉시 표시할 수는 없다. 작업 오류는 DB에 남고, 기존 시트 행의 ‘마지막 반영 시도시각’과 기준 버전으로 오래된 자료임을 구분한다. 복구 후 확인된 기존 행에 최신 상태를 반영한다. 별도 담당자 문자/메일 알림은 추가하지 않는다.

새 전달 스위치는 `DAECHION_ORDER_READY_MESSAGE_ENABLED`, `DAECHION_ORDER_SHEETS_ENABLED`이고 공통 `DAECHION_ORDER_WORKER_ENABLED`가 기본 비활성이다. 문자는 현재 결제 조회 스위치가 켜져야 하며 기존 단건 완료 문자와 동시에 활성화할 수 없다. 새 시트 대상은 `DAECHION_ORDER_SHEETS_SPREADSHEET_ID`·`DAECHION_ORDER_SHEETS_SHEET_ID`로 명시한다. 기존 `GOOGLE_SHEET_ID`와 단건 업무 파일/탭 설정을 대조한다. 현재 운영 변수·실제 시트·문자 설정은 변경하지 않았다.

반복 실행 스케줄·세션 유지, 계정/등록 결과 불명·기한 후 결제의 추가 수동 복구 조치, 실제 새 탭 초기화·연결 및 통합 검수는 다음 단계다. 기존 학생의 청구 전 관리자 확인 경로는 아래와 같이 구현했다.

### 지정 주문 작업자 실행부·청구 전 검사

`workers/daechion/orders.cjs`는 새 주문 전용 실행부다. 기존 `billing.cjs`와 별도이며 두 이미지에 포함한다. 이미지의 기본 시작 명령은 기존과 동일하다. 새 실행부도 인자 없이 실행하거나 `--check`를 주면 두 원장의 이력/체크섬·필수 구조를 읽기 전용 트랜잭션에서 확인하고 종료한다. 공급자 생성·조회·청구·문자·수강 등록·시트 쓰기는 하지 않는다. `schemaChecked`는 DB 준비 확인이며 외부 공급자 전체 연결이나 실제 판매 검수를 통과했다는 의미가 아니다.

검수 실행은 `node workers/daechion/orders.cjs --once --order-id <주문_UUID>`만 제공한다. `DAECHION_ORDER_WORKER_ENABLED` 및 개별 단계 스위치 외에, `DAECHION_ORDER_ACCEPTANCE_ID`와 DB의 불변 `request_fingerprint`에 맞춘 `DAECHION_ORDER_ACCEPTANCE_FINGERPRINT`가 필요하다. 별도 비공개 환경변수에 설정하고, 전화번호·API 키·인증 파일 내용을 명령행 인자로 넣지 않는다. 지정 주문이 없거나 ID·지문·테넌트가 다르면 공급자를 만들기 전에 중단한다. 포괄적 `--loop`나 대상 없는 `--once`는 거부한다. 청구 번호·수신 번호를 공개 입력으로 덮어쓸 수 없다.

실행 순서는 현재 결제/권한 처리 후 완료 안내, 최신 Sheets 반영이다. 비활성 단계의 공급자를 생성하지 않는다. 활성 단계의 공급자 설정은 첫 처리 전에 준비하며, 기존 원본/단건 업무 시트를 신규 주문 대상으로 지정하면 처리 전에 중단한다. 학생 조회 검수 플래그가 없으면 청구/등록을 거부하고, 결제 조회 없이 등록하거나 접근 정책 검수 없이 등록/완료 문자를 보내는 설정도 거부한다. 기존 단건 청구·등록·문자와의 동시 쓰기 제한은 유지한다.

`preflight.ts`는 확정 주문의 구성·금액과 현재 강의 ID·열림 상태·차시를 재검사한다. 테넌트와 학생/보호자 번호는 읽기 전용으로 조회하며 결제 번호는 신원 판정에 쓰지 않는다. 확정 뒤 상품 가격이 바뀌어도 청구 금액을 바꾸지 않는다. 누락/중복 ID, 닫힌 강의, 차시 없음, 조회 실패, 60초 초과, 기존/신규 불일치 또는 보유 권한 불명은 보류한다. 공식 API는 기존 학생의 보유 권한을 증명하지 못하므로 자동으로 미구매라고 간주하지 않는다. 청구 전 관리자 확인 경로는 아래 규칙을 충족할 때만 사용한다.

예상하지 못한 처리 예외는 `worker_execution_unknown` 사유로 원장에 보류를 시도하고 같은 실행의 완료 안내를 막는다. 이후 Sheets는 가능한 경우 최신 보류 상태를 반영한다. DB 자체가 끊기면 같은 DB에 오류를 기록할 수 없으며, 실행 결과는 실패로 남긴다. 외부 예외 본문·키·전화번호를 로그로 직렬화하지 않는다. 결과 불명 청구/계정/문자의 기존 재실행 금지 규칙은 그대로 적용한다. 관리자 화면의 보류·기록된 권한 재확인 조치는 아래와 같다.

시트 초기화는 `--setup-sheets`로만 명시적으로 수행하며 공통 작업자·Sheets 스위치가 모두 켜져 있어야 한다. 기본 점검이나 주문 처리에서는 자동으로 시트 열을 만들지 않는다. 현재 실제 원격 초기화는 하지 않았다. 정기 처리 스케줄·브라우저 세션 유지·운영 명령 전환·실제 신규 주문 검수는 후속 단계다.

### 별도 주문 DB 적용 도구

`scripts/daechion-order-migrations.cjs`와 `scripts/daechion-order-db.cjs`를 추가했다. 기본/브라우저 작업자 이미지 모두 새 도구와 주문 SQL 열 파일을 포함한다. 이미지의 기존 시작 명령과 기존 V1 마이그레이션 목록은 유지한다. 도구를 가져오는 것만으로 연결하거나 DB를 변경하지 않는다.

- `npm run db:daechion-orders:status`: 별도 원장의 적용 이력·체크섬과 미적용 파일을 읽기 전용 트랜잭션에서 확인한다. 인자 없는 스크립트 직접 실행도 status다.
- `npm run db:daechion-orders:check`: 미적용 파일, 누락된 작업자/안내 열, 비활성·누락·다른 함수에 연결된 보호 트리거가 있으면 실패한다. 상태 출력에는 연결 문자열·이름/전화번호·비밀번호를 포함하지 않는다.
- `npm run db:daechion-orders:migrate -- --database <실제_DB명>`: `DAECHION_DATABASE_URL`로 연결된 DB의 실제 이름과 인자가 일치해야 적용한다. 새 원장 전용 잠금·전체 트랜잭션 안에서 미적용 파일만 실행하고 이력을 저장한다. 중간 실패는 앞선 DDL·이력까지 되돌린다. 기존 스키마가 있는데 적용 이력이 없으면 임의 인수·삭제하지 않고 중단한다. 체크섬 변경, 이력 누락/순서 오류, 미지원 후속 버전도 중단한다.

이름 대조는 잘못된 대상 적용을 줄이기 위한 장치이며 서로 다른 서버의 동명 DB를 구분하지는 않는다. 운영 적용 전 연결 대상 서비스도 확인해야 한다. 모든 명령은 서버의 비공개 환경변수에서 연결 정보를 읽으며, 명령행에 URL이나 비밀번호를 붙이지 않는다. 실제 운영 DB에는 아직 적용하지 않았다. 운영 적용 후에도 접수·청구·문자·등록 스위치는 자동으로 켜지지 않는다.

격리된 DB 검사에는 전체 적용/재실행, 구버전 업그레이드, 이력 누락/변경, 부분 실패 롤백, 출처 불명 스키마 보존, 보호 트리거 비활성, 배달 열 누락을 포함한다. GitHub에서는 기존 원장/서비스 테스트 뒤에 직렬로 실행해 같은 검수 DB의 스키마 정리가 다른 검사와 충돌하지 않게 한다.

미래 운영 반영은 별도 주문 마이그레이션 도구로 명시적으로 수행한다. 기존 V1 실행부의 자동 마이그레이션에 슬쩍 추가하지 않는다. 새 기능이 구현/검수되기 전에 관리자 묶음 저장 버튼이나 공개 장바구니를 먼저 켜지 않는다.

### 일괄 주문 관리자 목록·보류·권한 재확인

`/admin/daechion/orders`와 `/api/admin/daechion/orders`를 추가했다. 기존 단건 신청 관리에서 별도 링크로 이동하며 단건 목록/조치 API는 변경하지 않았다. 기존 관리자 인증과 `DAECHION_ADMIN_ENABLED` 외에 새 `DAECHION_ORDER_ADMIN_ENABLED=true`, DB·테넌트·허용 출처 설정이 모두 필요하다. 새 설정은 기본 비활성이며 현재 운영에 켜지 않았다. 인증이 없으면 조회/수정 모두 401, 준비되지 않았으면 503이다. 인증을 통과한 조회도 테넌트를 제한하며 응답은 no-store다.

목록은 학생·학부모 이름/학생·보호자·결제 번호의 문자 그대로 검색, 확인 필요 필터, 50건 단위 페이지를 지원한다. 상세에는 원 단위 상품별/합계 금액, 입력 연락처, 청구 번호·현재 여부·조회 시각, 강의 고유 ID별 등록/권한 상태, 안내 수신 번호별 상태, 최근 작업 오류와 관리자 조치 이력이 있다. 조회는 읽기 전용 스냅샷 트랜잭션으로 일관된 버전을 보여 준다. 공급자 API나 청구/권한 변경을 조회 과정에서 호출하지 않는다.

현재 연결한 조치는 다음 두 가지다.

- 자동 처리 보류: 추가 자동 등록과 완료 안내를 중단한다. 이미 검증한 권한은 삭제하지 않고 실제 결제 취소/환불/권한 회수도 실행하지 않는다. 기존 확인 필요 사유가 있으면 보존한다.
- 등록된 강의 권한 재확인 대기: 최근 3분 내 현재 청구의 정상 결제 확인, 확정 학생 ID, 등록 성공 기록·차시 근거, 대상 강의 REVIEW 상태를 모두 충족할 때만 PENDING으로 바꾼다. 웹 요청에서 대치온에 다시 등록하거나 권한을 쓰지 않고 다음 작업자가 콘텐츠 권한만 재확인한다. 다른 강의의 완료 상태는 보존한다. 결제 취소·조회 노후·등록 결과 불명·강의 ID 불일치·이미 완료 상태는 거부한다.

담당자 입력·사유·명시적 확인·예상 주문 버전·요청 UUID가 필요하다. `004_admin.sql`은 새 원장 전용 관리자 이력을 추가하며, 같은 트랜잭션에서 조치·버전 증가·Sheets 후속 작업·이력을 함께 저장한다. 이력 저장이 실패하면 조치도 되돌린다. 같은 요청 UUID와 내용의 재전송은 한 번만 반영하고 이전 결과를 돌려주며, 내용이 다르거나 다른 변경으로 버전이 바뀌면 409다. 이력 수정/삭제는 DB 트리거가 거부한다. 담당자 이름은 기존 공용 관리자 인증에서 직접 입력한 기록이며 개인별 로그인 신원 증명은 아니다.

화면은 응답 유실/5xx 때 입력을 잠그고 동일 요청 재확인을 제공한다. 저장이 확인된 뒤 상세 재조회가 실패하면 저장 성공을 유지하고 새로 불러오기를 요구한다. 키·공급자 원문 오류를 표시하지 않는다. 허용하지 않은 재개/결제 강제 확정/계정 재생성/문자 재발송 같은 조치는 API 스키마에서도 거부한다. 청구 전 보류 해제와 기존 학생 확인은 아래에 추가했다. 현재 정상 승인 재조회에 의한 보류 해제와 기존 Sheets 행 복구 요청은 아래에 추가했다. 수동 권한 확인·회수 기록은 아래에 추가했다. 계정 연결이 불명확한 경우의 정리 등 나머지 결과 불명 조치는 추가 구현이 필요하다.

가상 데이터로 인증·출처·본문 크기·테넌트 격리, 동시 동일 요청 1회 반영, 오래된 버전 거부, 이력 저장 실패 롤백, 이력 불변, 유효/불가 권한 재확인을 검사했다. 로컬 실제 Chromium 화면 검수는 `node tests/daechion-order-admin-preview.mjs --local-only`로 실행한다(별도 브라우저 의존성과 Chrome 필요). 응답 유실 후 동일 요청 복구·두 종류 조치·모바일 폭·브라우저 오류 없음까지 확인하며 실제 공급자/원격 DB/Sheets를 사용하지 않는다.

### 기존 학생 확인과 청구 전 보류 해제

`005_manual_review.sql`과 `manual-review.ts`를 추가했다. 새 관리자 조치는 기존의 조회/보류/권한 재확인 설정 뒤에서만 활성화된다. 실제 원격 DB에는 적용하지 않았다.

- 기존 학생·전체 강의 미보유 확인(APPROVE_EXISTING): 청구 기록이 전혀 없고 결제 대기·학생 연결 대기 상태인 주문만 허용한다. 담당자는 대치온 학생 ID와 모든 구성 강의 ID를 확인하고, 해당 학생이 모든 강의를 보유하지 않았음을 명시적으로 확인한다. 하나라도 기보유 강의가 있으면 이 경로로 승인하지 않는다. 일부 강의를 빼거나 묶음 가격을 변경하지 않는다.
- 서버는 승인 전에 테넌트, 학생 상세, 학생·보호자 번호 검색 결과를 읽기 전용으로 대조한다. 정확한 이름·학생 번호·선택 보호자 번호(두 번째 보호자 포함)가 선택 ID에 연결돼야 한다. 비활성 여부는 거부 사유가 아니다. 동일 이름만으로 선택하거나 결제 번호에 로그인 권한을 주지 않는다. 이 단계에서는 계정 생성/등록 API를 사용할 수 없다.
- 모든 구성 ID·주문/연락처/금액의 불변 맥락·프로필 지문·원래 신청 지문·서버 조회 시각을 감사 기록에 묶는다. 외부 조회는 DB 트랜잭션 밖에서 하고 저장 직전에 버전과 60초 이내의 조회 근거를 다시 확인한다. 원래 NEW/EXISTING 선택이나 연락처는 수정하지 않고 관리자 확인 이력을 함께 남긴다.
- 최초 REVIEW 견적은 유효한 같은 버전의 관리자 승인 기록과 정확한 전체 강의 구성이 있을 때만 CONSUMED 및 READY로 바뀐다. 관리자 승인 기록은 상태 전환과 같은 트랜잭션에 저장하며, 커밋 때 해당 버전 증가가 완료됐는지 검사한다. 기존 견적·주문 스냅샷, 합계/구성 검증과 학생 ID 고정 규칙은 유지한다. 기존 마이그레이션 파일의 체크섬은 변경하지 않는다.
- 청구 전 미보유 확인은 오래된 수동 확인을 무기한 재사용하지 않도록 15분간만 인정한다. 작업자는 현재 강의 상태와 선택 학생의 전화번호·프로필을 다시 조회한다. 지문 변경·확인 만료·조회 실패면 청구를 보류하고 관리자 재확인을 요구한다. 같은 요청의 재확인은 먼저 저장 결과를 확인하므로 이후 API 장애가 있어도 조치를 반복하지 않는다.
- 결제가 확인된 뒤에는 승인 당시 선택 ID와 현재 프로필을 재대조해 같은 기존 계정에 연결한다. 원래 체크박스와 다른 기존 학생 선택도 이 명시적 확인 기록이 있는 경우에만 허용한다. 확인한 기존 학생을 새로 생성하지 않는다. 이미 청구한 뒤에는 이 경로로 학생을 바꾸거나 계정 생성 결과 불명을 초기화할 수 없다.
- 청구 전 관리자 보류 해제(RESUME_UNBILLED): 기존에 확정된 주문이 관리자 보류만 남아 있고 청구 이력·학생 생성 시도·처리 중 신원 확보가 전혀 없을 때만 READY로 돌린다. 최초 미확인 REVIEW 접수나 결제/청구 결과 불명, 이미 청구한 주문, 오래된 기존 학생 승인에는 사용할 수 없다. 실제 청구는 다음 작업자의 사전 검사를 다시 통과해야 한다.

Sheets에는 유효한 관리자 확인을 ‘통과’와 확인한 학생 ID/전체 강의 미보유/청구 전 재검사 대기로 표시한다. 만료되거나 맥락이 달라지면 ‘확인 필요’로 바꾼다. 결제 후 실제 신원 연결이 완료되면 기존의 전화번호 대조 완료 표기를 사용하며, 이후 신원 불일치가 생기면 확인 필요가 우선한다. 이는 담당자의 직접 확인 기록이며 API가 보유 권한을 증명했다는 뜻은 아니다.

가상 데이터로 최초 REVIEW의 무승인 전환 차단, 기존 비활성 학생·보호자2 대조, 체크박스 불일치의 명시적 승인, 구성 누락/거짓 확인/신청 맥락 불일치 거부, 승인 만료/프로필 변경 보류, 동일 승인 재확인, 합산 청구 후 같은 학생 ID 등록(신규 생성 0건), 청구 결과 불명 재개 거부, 미완료 감사 기록 커밋 거부를 검수했다. 실제 학생/청구/문자/대치온 변경은 하지 않았다. 결제 후 보류·수동 등록/회수·Sheets 복구·정기 작업자는 아직 후속 작업이다.
청구를 시도한 뒤에는 학생 선택을 바꿀 수 없으므로, Sheets도 15분 경과만으로 재승인을 요구하지 않는다. 당시 확인한 학생으로 결제 후 재검사할 예정임을 표시한다. 이 경로의 유효기간은 청구 전에만 적용하며, 이후 신원 오류나 금융 오류는 각각의 확인 필요 표시가 우선한다.

### 현재 결제 재조회와 기존 Sheets 행 복구

006_recovery.sql, paid-recovery.ts, sheet-recovery.ts를 추가했다. 기존 공용 관리자 인증·일괄 주문 관리자 설정을 사용하며 기본 비활성 상태를 유지했다. 기존 마이그레이션 체크섬과 단건 실행부는 변경하지 않았다. 운영 DB나 원격 설정에 적용하지 않았다.

RESUME_PAID는 보류/대기 종료된 주문의 현재 청구서에 대해 담당자가 금액·승인일시·완료 상태를 확인한 후 요청한다. 웹 서버는 결제선생을 읽기 전용으로 다시 조회한다. 현재 청구서 ID·공급자 계정·원 단위 금액·발송/대기 종료 시각 안의 승인·기존 승인 근거가 모두 일치해야 한다. 발송 결과 불명, 현재 취소/파기, 미납/조회 불명, 기한 후 결제, 승인 근거 변경은 이 경로로 강제 확정하지 않는다. 이 서버 조회에는 비공개 PAYSSAM_API_KEY/MEMBER/MERCHANT 및 기존 콜백 URL 설정이 필요하며, 실제 연결은 후속 운영 단계에서 확인한다.

읽기 전용 조회는 트랜잭션 밖에서 하고 저장 직전 주문 버전·불변 신청 지문·청구 레코드·공급자·마이크로초 조회 토큰·60초 이내 근거를 재대조한다. 중간에 다른 조회/취소/수동 조치가 발생하면 저장하지 않는다. 정상 근거가 있을 때만 현재 결제 기록을 갱신하고 주문 보류를 해제한다. 청구서를 다시 발송하거나 결제를 실행하지 않는다. 계정 생성 결과 불명·신원 처리 중·신원 확인 필요는 재개하지 않는다. 등록 결과 불명인 강의도 다시 등록하지 않고 REVIEW로 남긴다.

완료 안내는 수신 기록이 없고 작업 시도도 전혀 없는 것으로 확실한 건만 다시 대기시킬 수 있다. UNKNOWN/SENT 안내 상태, 수신 기록(PENDING/BLOCKED 포함), 시도한 작업은 초기화하지 않는다. 기존 권한과 수신 번호별 기록을 보존하며 실제 안내/권한 처리는 다음 작업자가 현재 결제와 권한 상태를 다시 확인한 뒤 진행한다. 이 조치 자체에서는 등록/권한/문자 API를 호출하지 않는다.

RECONCILE_SHEETS는 담당자가 해당 주문의 기존 업무 시트 행을 직접 확인한 뒤 요청한다. 서버는 그 주문에 정확히 하나의 UNKNOWN 시트 작업이 있고 다른 처리/복구가 진행 중이지 않은지 확인한다. 조치·주문 버전 증가·감사 기록·대상 작업 ID에 연결된 복구 요청을 한 트랜잭션에 저장한다. 승인 이력과 복구 요청이 다른 주문/작업을 가리키면 커밋이 거부된다. 동일 요청의 응답 유실 후 재확인은 새 복구를 만들지 않는다.

작업자는 전용 Sheets 단계가 활성일 때만 복구 요청을 확보한다. 주문/작업/승인/임대 토큰을 대조하고, 기존 행 전용 갱신 모드로 원래 게시기를 호출한다. 행의 주문번호·메타데이터·헤더를 확인하며 직원 메모는 보존한다. 복구 경로에서는 행을 삽입하지 않는다. 행 없음·중복 표식·헤더 변경·API 결과 불명은 UNKNOWN으로 남겨 자동 재시도하지 않는다. 중단된 복구의 임대가 끝나면 UNKNOWN으로 표시하고, 새로운 담당자 확인 없이 다시 실행하지 않는다. 이후 명시적 재확인으로 같은 기존 행을 다시 갱신할 수 있다. 사라진 행/표식의 재생성이나 임의 데이터 삭제는 제공하지 않는다.

관리자 화면은 현재 청구서·금액 확인, 기존 시트 행 확인, 대상 오류 작업 ID, 복구 요청 상태와 근거 이력을 표시한다. 시트 자체가 끊겼거나 표식이 깨졌을 때 그 오류를 같은 시트에 즉시 쓸 수는 없으며, DB/관리자 화면에 남은 결과와 마지막 반영 시각을 확인해야 한다. 정상 게시가 가능해지면 최신 상태를 기존 행에 반영한다. 담당자 문자/메일 알림은 추가하지 않았다.

가상 데이터로 현재 정상 승인 복구, 조회 토큰 변경 거부, 잘못된 금액/계정/승인/취소/기한 후 결제 거부, 계정 생성 결과 불명 차단, 시도한 문자 보존, 같은 요청 1회 반영을 검사했다. Sheets는 삽입 응답 유실 후 기존 행 1개 갱신, 직원 메모 보존, 행 없음 시 삽입 금지, 만료된 복구 임대 차단, 새 확인 뒤 복구, 승인/대상 연결 검사를 포함했다. 실제 청구·환불·대치온 변경·문자·원격 시트 쓰기는 하지 않았다. 수동 권한 확인·회수 기록은 아래에 추가했다. 계정 연결 불명 등 나머지 예외 정리·정기 실행·운영 연결 및 통합 검수는 남아 있다.

### 대치온 수동 권한 확인·회수 완료 기록

007_manual_access.sql과 manual-access.ts를 추가했다. 두 조치는 대치온에서 이미 수행한 작업을 기록하며, 웹 요청에서 학생 생성/등록/권한 부여/회수/환불/문자 발송 API를 호출하지 않는다. 기존 일괄 주문 관리자 인증·테넌트·출처·크기 제한·요청 UUID·예상 버전·담당자/사유/명시적 확인과 기본 비활성 정책을 유지한다. 운영에는 아직 적용하지 않았다.

MANUAL_ACCESS는 이미 학생 ID가 확정된 주문의 PENDING/REVIEW 강의에 대해 사용한다. 관리자는 대치온에서 해당 학생을 등록하고 차시 영상·차시 자료·강의 자료 권한을 직접 확인한 후 세 항목을 각각 확인한다. 서버는 기존에 연결된 학생 ID, 현재 이름/학생·보호자 번호(보호자2 포함), 테넌트, 정확한 강의 ID와 열린 강의의 현재 차시 목록을 읽기 전용으로 확인한다. 60초 이내의 서버 조회 근거와 신청 맥락을 저장 직전 다시 대조한다. 최근 정상 결제 근거가 없거나 학생 연결이 불명확하거나 처리 중인 신원/권한 작업이 있으면 기록하지 않는다. 결제 근거가 오래된 경우 기존 결제 재조회/보류 해제 경로를 먼저 사용한다.

승인한 강의만 MANUAL로 기록하고 실제 API 등록 성공 여부는 보존한다. API 결과가 불명확했던 건을 수동 확인했다고 해서 enrollment_recorded를 true로 바꾸지 않는다. 감사 이력·강의 상태·현재 차시 근거·버전·Sheets 후속 작업은 한 트랜잭션으로 저장하며, 대상 학생/강의·현재 버전·감사 기록이 다르면 DB도 거부한다. 모든 구성 강의가 검증/수동 확인된 뒤에만 안내를 대기시킬 수 있고, 이미 시도했거나 수신 기록이 있는 문자는 초기화하지 않는다. 직접 확인하지 못한 권한을 자동 API 검증 완료로 표시하지 않는다.

RECORD_REVOKED는 이미 연결된 학생의 특정 강의 권한을 대치온에서 직접 회수한 뒤 저장한다. 서버는 같은 학생 ID와 현재 연락처를 다시 대조하지만 현재 결제 완료나 강의 열림을 요구하지 않아 취소/환불 이후와 닫힌 강의에서도 기록할 수 있다. 진행 중인 신원/권한 작업은 먼저 정리돼야 한다. 선택한 강의에 회수 시각·관리자 이력을 남기고 REVOKED로 표시하며, 해당 주문을 보류해 추가 자동 처리·안내를 멈춘다. 다른 강의의 완료 상태, 학생 ID, 청구서/결제 상태와 과거 문자 기록은 바꾸지 않는다. 실제 환불은 결제선생에서 따로 처리한다.

회수된 강의는 일반 자동 재개·권한 재확인·수동 확인 경로로 다시 열리지 않는다. DB도 REVOKED의 상태/회수 이력을 변경하거나 그런 강의가 있는 주문을 READY로 돌리는 것을 차단한다. 이는 회수 기록을 자동화가 되돌리지 못하게 하는 경계이며, 잘못 기록한 회수의 별도 정정/재부여 절차는 이번 범위에 포함하지 않았다.

관리자 화면에는 고정 학생 ID, 대상 강의 ID, 세 권한 확인 또는 회수 확인, 확인한 차시 목록, 회수 시각과 담당자 이력을 표시한다. Sheets는 MANUAL을 수동 권한 확인으로, REVOKED를 수동 회수 확인으로 표시하고 보류 사유를 함께 반영한다. 이 기능은 이미 연결된 학생 대상이며 계정 생성 결과 불명이나 연락처 변경의 강제 정합성 처리를 대신하지 않는다.

가상 데이터 검사에는 API 결과 불명 강의의 수동 확인, 전체 확인 전 안내 차단, 등록 성공 근거 보존, 불명 문자 재발송 금지, 잘못된 학생/강의/누락 확인 거부, 오래된 결제·진행 중 작업·조회 실패·이력 저장 실패의 원자적 중단을 포함했다. 회수 기록은 다른 강의 보존·자동 재개 차단·취소 후 기록·감사 없는 MANUAL 전환 차단을 확인했다. 실제 학생/결제/권한/문자/원격 시트는 변경하지 않았다. 다음 단계는 계정 연결 불명과 미확인 접수 정리, 정기 실행·세션 유지, 원격 연결 및 실제 일괄 결제 검수다.


## 학생 생성 결과 불명 복구

008_identity_recovery.sql과 identity-recovery.ts를 추가했다. RECONCILE_IDENTITY는 결제 후 생성 요청의 결과가 불명확한 주문에서 담당자가 대치온에 실제 생성된 계정을 확인한 사실을 기록한다. 현재 단계는 개발 브랜치이며 운영 DB·설정에는 적용하지 않았다.

대상은 결제 PAID·확정 접수·REVIEW 상태이며 identity_create_unknown/identity_unknown, 실제 생성 시도 기록, 학생 확인 REVIEW, 활성 신원 토큰 없음, 모든 강의 PENDING·API 등록 성공 기록 없음이 필요하다. 이미 저장된 학생 ID가 있으면 같은 ID만 허용한다. 담당자가 학생 ID와 생성 결과 직접 확인을 입력하면 서버는 기존 읽기 전용 조회로 테넌트·학생 상세·이름·학생 번호·선택 보호자 번호(보호자2 포함)를 대조한다. 결제 번호는 신원에 사용하지 않는다. 조회 근거는 전체 강의·신청 스냅샷·주문 버전과 연결되며 60초 내 저장해야 한다. 새 학생 생성 API는 호출하지 않는다.

학생 ID·프로필 지문·전체 강의 ID·원래 신청 지문·조회 시각·담당자·사유는 변경 불가능한 감사 기록에 저장한다. 주문을 PASSED 신원으로 고정하고 해당 주문의 전화번호 잠금만 해제한다. 원래 신청/기존·신규 선택과 생성 시도 기록은 보존한다. 상태는 REVIEW/identity_reconciled로 유지하므로 권한 등록·완료 안내는 실행되지 않는다. 이후 별도 RESUME_PAID에서 현재 청구서의 금액·정상 승인·기한을 재조회해야 재개할 수 있다. 작업자는 고정 학생과 프로필 지문을 다시 대조하며 다시 생성하지 않는다. 취소·조회 불명·프로필 변경은 계속 보류한다.

008의 DB 트리거도 복구 감사·같은 학생/전체 대상·버전·시간·상태를 검증하고, 복구 포인터/생성 시도 이력의 변경과 감사만 남는 미완료 커밋을 차단한다. 메시지 이력과 강의 상태는 수정하지 않는다. Sheets는 중복 학생 확인은 통과, 처리 확인은 결제 재조회 필요로 분리해 표시한다. 계정이 발견되지 않거나 정보가 다른 경우 자동 재생성하지 않는다. 미확인 신규 접수의 종료 및 생성되지 않은 것으로 최종 확인된 건의 별도 처리 절차는 후속 작업이다.


## 미확인 신규 접수 확인·청구 전 종료

009_intake_review.sql과 intake-review.ts, CONFIRM_NEW_INTAKE/CLOSE_INTAKE 조치를 추가했다. 기존 공용 관리자 인증·테넌트/출처 검사·UUID/버전·담당자/사유·명시적 확인 정책을 사용하며 기본 비활성이다. 기존 001~008 SQL 체크섬과 운영 설정은 바꾸지 않았다.

신규 학생 접수 확인은 NEW로 신청한 REVIEW 주문 중 청구 이력·계정 생성 시도/신원 토큰·수강 등록 시도·안내 수신 이력이 없는 건에만 허용한다. 서버의 읽기 전용 사전 검사로 학생/선택 보호자 번호에 기존 프로필이 없는지(보호자2 포함), 테넌트와 전체 강의 고유 ID·개설 상태·차시 구성이 정상인지 확인한다. 조회 실패·기존 번호·잘못된 선언은 승인하지 않는다. 기존 학생은 APPROVE_EXISTING을 사용한다. 조회 근거는 전체 강의/신청과 연결해 60초 내 저장하며 신청 스냅샷·가격·구성을 보존한다. 최초 접수 확인·견적 소비·감사 기록·버전 증가·시트 후속 작업을 같은 트랜잭션에 저장한다. 이 요청에서 실제 청구·학생 생성·등록·문자는 실행하지 않는다. 작업자는 발송 직전 별도 현재 조회를 다시 수행한다. Sheets는 신규 번호 재조회 통과와 작업자 재검사 대기를 표시한다.

청구 전 종료는 READY/REVIEW·PENDING·WAITING 신원·학생 ID 없음·생성 시도/토큰 없음에 더해 청구 이력이 전혀 없고 모든 강의가 미시도 PENDING이어야 한다. 결제/청구/학생 생성/등록 결과 불명은 종료하지 않는다. 종료 시 CLOSED/intake_closed와 불변 감사 포인터를 기록하고, 미소비 견적만 EXPIRED로 변경한다. 원래 신청·상품·금액·확정 시각·관리자 이력은 보존한다. 삭제·환불·대치온 변경·문자 발송은 하지 않는다. 정상 종료는 업무 시트에 접수 종료로 표시하며, 별도 시트 장애가 있으면 계속 확인 필요로 남긴다.

종료한 주문은 재개하지 않는다. DB 보호 트리거도 상태 재개/포인터 변경과 청구 생성을 거부한다. 종료 직전에 시작한 청구 전 읽기 검사는 주문 버전 대조에서 중단한다. 청구서가 이미 예약된 경우에는 종료를 거부한다. 같은 요청 재실행은 1회만 반영하고 저장 실패는 전체 롤백한다. 이후 구매하려면 새 견적으로 새 신청을 받으며 기존 주문 기록은 유지한다. 계정 생성 결과 불명이나 이미 결제한 건의 종료는 이번 조치의 범위가 아니다.


## 정기 실행·브라우저 세션 유지

010_scheduler.sql, scheduler.ts와 orders.cjs --loop를 추가했다. 인자 없는 실행/--check는 계속 읽기 전용 점검이다. --once --order-id는 기존 지정 주문/신청 지문 검수 방식 그대로다. 정기 실행은 DAECHION_ORDER_WORKER_ENABLED=true 및 별도 DAECHION_ORDER_LOOP_ENABLED=true와 --loop가 모두 필요하다. 검수 전용 DAECHION_ORDER_ACCEPTANCE_ID/FINGERPRINT가 남아 있으면 --loop를 거부한다. 각 청구/결제 조회/등록/안내/시트 스위치는 별도이며 기존 단건 청구/등록/안내와 동시 활성화하는 구성은 계속 거부한다. 운영 변수·기존 시작 명령은 아직 바꾸지 않았다.

테넌트별 DB 세션 advisory lock(61134)을 전 주기 동안 유지하며 트랜잭션을 길게 열어 두지 않는다. 경쟁 복제본은 외부 공급자를 생성하기 전에 대기한다. 연결이 끊기면 후속 DB 단계/작업을 차단하고 해당 연결을 버린다. 이미 시작한 외부 호출은 기존 write-ahead/신원 토큰/강의 임대/메시지 수신/시트 임대로 보호하며 결과 불명은 초기화하지 않는다. 이 잠금은 반복 작업자끼리의 배제이며 별도 지정 검수 실행과의 동시 쓰기는 기존 단계별 DB 보호를 따른다.

매 주기 최대 10건을 순서대로 처리하고 주기 종료 후 30초 대기한다. 기존 진행 중/조회 대상 청구서, 미처리 등록, 실행 가능한 안내/시트 또는 담당자가 승인한 시트 복구를 대상으로 한다. 순서는 다음 실행 시각/접수 시각/ID이며 작업 시작·종료·다음 시각·확인 버전을 DB에 저장한다. 실패는 60초 뒤, 진행 중은 30초 뒤, 완료/보류된 결제 조회는 5분 뒤 확인한다. 담당자 변경으로 주문 버전이 증가하면 다음 확인 시각 이전에도 대상으로 들어간다. 완료 강의는 다시 등록하거나 프로필을 다시 연결하지 않는다. 실제 권한 상태가 바뀐 경우 수동 조치와 기존 결제 재조회 절차를 사용한다.

정기 등록을 사용하려면 DAECHION_ORDER_SESSION_MAINTENANCE_ENABLED=true와 DAECHION_BROWSER_CHECK_LECTURE_ID(안전한 점검용 강의 ID)가 필요하다. 기존 공식 API+브라우저 제공자의 refreshSession을 사용하며 학생 등록이나 권한 변경을 하지 않는 관리자 수강생 목록 조회로 세션을 확인한다. 기존 암호화 browser_sessions 저장소와 세션 잠금(61109)을 그대로 사용한다. 인증 파일/키를 새 테이블에 복제하지 않는다. 성공은 DB에 READY/다음 15분, 실패·중단은 FAILED 또는 UNKNOWN/다음 60초로 기록해 재시작 후에도 상태를 이어간다. 구 단건 세션 전용 프로세스와 동시에 유지하면 세션 잠금 경쟁으로 잠시 보류될 수 있으므로 운영 전환 시 유지 담당 프로세스를 하나로 정한다.

세션 확인에 실패한 주기는 계정 생성·등록·권한 부여를 실행하지 않는다. 결제 조회와 기존 오류의 시트 투영은 계속 가능하다. 해당 주기에서 선택한 READY/PAID 미완료 주문에 session_issue를 기록하고 버전/시트 후속 작업을 생성한다. 관리자 상세와 시트 확인 필요 사유에 대치온 로그인 세션 확인 필요를 표시한다. 세션 회복 뒤 오류 표시를 정리하고 기존 결제/신원/권한 상태를 다시 검사한다. 개별 결과 불명 작업을 자동 초기화하거나 재생성·재발송하지 않는다. 세션 유지 자체가 인증 만료/폐기를 영구적으로 해결하지는 않으며, 새 로그인이 필요한 경우 기존 인증 준비/명시적 세션 재설정 절차로 운영자가 복구한다. DB/시트 자체 장애는 같은 시트에 즉시 알릴 수 없으므로 관리자 상태와 서버의 개인정보 없는 요약 로그를 확인한다.

SIGTERM/SIGINT는 새 주문 시작과 다음 주기 대기를 중단하고 현재 주문 처리는 마무리한다. 강제 종료 시 기존 결과 불명 보호를 따른다. 로그에는 처리/실패 건수·세션 정상 여부와 고정 오류 코드만 남기며 학생 ID/전화번호·키·인증 파일·공급자 오류 본문은 출력하지 않는다. 이번 단계는 코드와 가상/격리 DB 검증이며 실제 정기 실행·운영 연결·금융/LMS 쓰기는 별도 통합 검수 단계다.
