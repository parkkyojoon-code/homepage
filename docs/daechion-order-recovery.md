# 주문 장애 격리와 복구

## 적용 범위

브라우저 전체 실행 제한, 단계별 설정 오류 격리, 결제 후 학생 조회 재시도·관리자 복구, Sheets 최초 반영 전 조회 장애의 복구를 다룬다. 결제 근거의 3분 유효기간과 상품 JSON 저장 방식은 이번 변경 범위에서 제외한다.

## 실행과 설정 점검

`orders.cjs --check`는 DB 스키마와 활성 단계의 공급자 준비 상태를 읽기 전용으로 확인한다. 결과의 `providersReady`는 결제·API·구매자 검증 비밀값·브라우저·문자·Sheets 준비 상태를 표시하며, 활성 공급자 설정이 불완전하면 점검 명령은 실패한다. 반복 실행은 정상적인 다른 단계의 처리를 계속한다.

문자나 Sheets 초기화 실패는 해당 단계만 대기시킨다. 기존 결제 조회·등록을 보조 기능 설정 오류로 중단하지 않는다. 청구용 비밀값/API 설정이 없으면 새 청구를 대기시키며 기존 결제 확인은 가능한 범위에서 진행한다. 설정 오류는 자동화 점검 기록에 제한된 단계 코드로 남기며 공급자 오류 원문·비밀값을 저장하지 않는다.

새 작업자 프로세스는 이전 프로세스가 저장한 READY 캐시를 첫 인증 점검의 근거로 사용하지 않는다. 인증이 준비되지 않으면 신규 청구·자동 등록을 대기시키고 결제 조회와 Sheets는 계속한다. DB 연결/잠금 장애로 주기가 끝나면 다음 주기에서 원장의 처리 기록을 확인한다. 미확정 청구·계정 생성·등록·문자는 이 방식으로 맹목적으로 재실행하지 않는다.

브라우저의 초기화·인증·검수·정리 제한과 종료 확인은 `daechion-browser-lifetime.md`를 따른다. 종료를 확인하지 못한 공급자는 격리하며 로그의 `browserRestartRequired:true`를 표시한다. 격리가 발생하면 같은 주문의 다음 강의와 후속 주문도 계정 생성·등록을 시작하지 않고 대기한다. 종료 불명 상태에서 새 브라우저를 계속 열지 않는다.

## 청구 발송 응답 유실 후 결제 복구

`bill_send_unknown`은 청구서가 실제 발송됐을 수 있어 재발송하지 않는 상태다. 결제선생에서 해당 청구가 결제 완료됐다면 관리자 주문 상세에서 다음 순서로 복구한다.

1. 실제 청구번호·금액·승인시각·결제 완료 상태를 결제선생에서 확인한다.
2. **청구 발송 결과·결제 대조 기록**을 선택하고 담당자·확인 근거와 확인 항목을 저장한다. 서버도 같은 결제 계정의 같은 청구를 다시 조회한다.
3. 이 단계는 같은 청구의 발송·결제 사실만 기록한다. 주문은 보류를 유지하며 청구 재발송·학생 생성·수강 등록·안내 문자는 실행하지 않는다.
4. **현재 결제 재조회 후 보류 해제**를 별도로 실행한다. 현재 결제가 다시 확인돼야 작업자가 정상 처리를 재개한다.

원래 발송 시도 시각과 7일 기한을 유지한다. 기한 후 결제, 취소·파기, 금액 불일치, 조회 실패, 원래 시도를 입증할 수 없는 과거 기록은 이 기능으로 복구하지 않는다. 확인하는 사이 주문이나 결제 관측이 변경되면 저장을 거부한다. 응답을 받지 못했으면 화면의 **같은 요청 결과 다시 확인**으로 기존 감사 기록을 조회한다.

이 기능에는 `013_bill_send_recovery.sql`이 필요하다. 과거 발송 시도 시각은 청구 한 건과 원래 발송 이벤트 한 건으로 확실하게 연결되는 경우만 보완한다. 증거를 임의로 만들거나 미확정 기록을 일괄 초기화하지 않는다. 013 적용 후에는 이를 모르는 이전 migration runner로 스키마 검사를 통과할 수 없으므로, 이전 코드로 단순 롤백하지 않는다.

## 결제 후 학생 조회

일시적인 조회 실패는 학생 생성 전과 기존 학생 확인 후 모두 재조회한다. 초기 재시도 이후에는 최대 5분 간격으로 조회하며, 읽기 실패 횟수만으로 영구 보류하지 않는다. 횟수와 다음 확인 시각을 DB에 저장하므로 재시작이 재시도 간격을 초기화하지 않는다. 학생 생성 요청의 결과가 불명확하면 이 조회 재시도 규칙으로 생성 요청을 반복하지 않는다.

생성을 시도하지 않은 결제 완료 건이 학생 확인 보류로 남으면 관리자 주문 상세에서 다음 순서로 처리한다.

1. 대치온에서 실제 학생·학생 번호·보호자 번호와 구매 강의 보유 여부를 확인한다.
2. **결제 후 학생 계정 대조·연결**에서 정확한 학생 ID를 지정한다. 전체 구매 강의 미보유와 현재 결제를 다시 확인하도록 승인한다.
3. 서버는 단일·정확한 계정, 전체 강의, 현재 청구서·금액·승인 시각과 주문 버전을 검증하고 감사 기록에 묶는다. 검증된 계정을 연결해도 주문은 보류를 유지한다.
4. **현재 결제 재조회 후 보류 해제**를 실행한다. 그 뒤 작업자가 연결된 계정으로 미완료 등록만 진행한다.

서로 다른 강의를 별도 주문한 신규 학생의 첫 주문이 이미 계정을 만든 경우도 같은 확인 경로를 사용할 수 있다. 이름만 같거나 번호가 모호한 계정을 자동으로 연결하지 않는다. 생성 결과 불명 건은 기존의 생성 계정 대조 경로를 유지한다. 일부 등록이 이미 진행된 경우 계정을 다른 학생으로 다시 연결하지 않는다.

이전 버전에서 조회 실패로 보류된 신규 신청에 아직 대치온 계정이 없다면 **현재 결제 재조회 후 보류 해제**의 신규 학생 재확인 승인을 사용한다. 서버가 학생·보호자 번호 전체의 기존 계정 부재, 전체 구매 대상과 현재 결제를 새로 확인하고 감사 기록을 남긴 뒤에만 계정 생성 전 단계로 되돌린다. 이미 생성 요청을 보냈거나 등록을 시작한 주문, 기존·신규 선택 불일치나 모호한 번호 일치는 이 경로로 해제하지 않는다.

## Sheets 조회 장애

Sheets 작업은 요청을 보내기 전에 쓰기 시작 기록을 DB에 먼저 저장한다. 새 컬럼 `sheet_write_started`, `sheet_read_token`, `sheet_read_attempts`가 쓰기 전 실패와 쓰기 결과 불명을 구분한다.

- 쓰기 전 일시적인 조회 오류는 초기 재시도 후 최대 5분 간격으로 재시도한다. 연결이 복구되면 기존 행을 갱신하거나 첫 행을 한 번 생성한다.
- 헤더·연결 문제 등으로 쓰기 전에 보류된 건은 설정을 바로잡고 **Sheets 반영 복구 요청**을 사용할 수 있다. 화면에 쓰기 전 실패로 확인된 경우에만 최초 행 생성도 허용한다.
- 쓰기를 시작했거나 이전 작업자의 기록만으로 결과를 증명할 수 없는 건은 기존 행의 주문번호·메타데이터를 확인하는 복구만 허용한다. 행이 없다고 무조건 다시 삽입하지 않는다.
- 직원 메모 열과 기존 프로세스1 시트는 변경하지 않는다.

## 배포 순서

1. 전체 검사와 브라우저 이미지 검증을 통과한 버전으로 `011_identity_read_recovery.sql`, `012_sheet_read_recovery.sql`을 준비한다.
2. 기존 DB에 추가 마이그레이션을 먼저 적용한다. 이전 010 작업자가 잠시 함께 실행돼도 쓰기 불명 보호가 유지되는지 검증한 변경이다. 기존 마이그레이션 파일은 수정하지 않는다.
3. 신규 웹·작업자를 배포하고 스키마 준비 상태, 단계 준비 상태, 인증 유지와 주문 조회를 확인한다.
4. 마이그레이션은 읽기 재시도라고 증명된 과거 시트 오류만 재대기시킨다. 일반 UNKNOWN이나 미확정 생성·발송 기록을 일괄 초기화하지 않는다.
