# 강의 서비스 출시 전 진행표

2026-11-04 기준. 기능 범위를 추가하지 않고 현재 구현을 마무리하기 위한 점검표다. 검증 환경의 성공과 운영 배포를 구분한다.

운영 웹·DB·worker 연결값과 기존 저장소 보존 기준은 [lecture-production.md](lecture-production.md)를 따른다.

## 완료한 검증

- 별도 Railway 검증 웹·PostgreSQL 18.6·035까지 마이그레이션·개인 OWNER 관리자 연결.
- 구매자 가입·로그인·주문, 관리자 수동 오픈·회수·복원, 판매 종료 후 기존 구매 권한 유지.
- 구매자 비밀번호 초기화와 변경 후 기존 주문·강의실 유지.
- 사용자 승인에 따른 실청구 1,200원 발송·미납 조회·실결제 확인·자동 권한 부여·구매자 강의실 표시.
- 실제 결제 이력에 정확한 금액과 '자동 강의 오픈' 기록, 수동 승인 이력 없음 확인.
- 발송 후 추가 발송 비활성, 조회 전용 작업자 실행.
- 사용자 지정 영상 등록 후 결제 구매자의 강의실 링크로 YouTube '원서상담 공지' 영상 진입·실제 재생(0:00 → 0:11)을 확인하고 일시정지. 판매 종료와 기존 구매 권한 유지. 비로그인 영상 접근 401 및 원본 URL 비노출 확인.
- 실제 결제 검수 주문의 수동 회수 → 강의실 제외·사이트 직접 접근 거절 → 복원 → 관리자 재조회 → 자동 처리 복귀를 실제 브라우저에서 확인. 회수 중 F가 다시 조회돼도 자동으로 열리지 않고, 사유·처리자·조회 결과가 기록됨을 확인했다. 최종 상태는 PAID / AUTO / 이용 가능이다.
- 결제 연동 후 비로그인 접근 및 교차 Origin 차단 등 검증 환경 HTTP 점검 12건 통과.
- 기존 경로 /, /classes, /curriculum, /my, /admin, /terms, /privacy의 검증 환경 HTTP 렌더링 7건 통과. 기존 신청·학생 파일을 수정하는 제출은 하지 않았다.

HTTP 렌더링 성공은 기존 신청서 제출·Sheets 쓰기·기존 학생 로그인의 전체 회귀 성공을 뜻하지 않는다. 실제 고객 데이터로 임의의 시험 제출을 하지 않는다.

## 실제 영상 검수 절차

2026-11-04 아래 등록·구매자 접근·재생을 완료했다. 비로그인 접근과 권한을 회수한 계정의 사이트 접근도 차단된다. 다른 구매자 소유권 구분은 앞선 별도 계정 HTTP 검수와 실제 SQL 테스트에서 확인했다. 이번 영상의 권한 없는 상태 검수는 회수된 검수 계정으로 수행했다.

1. 사용자가 지정한 사용 가능한 YouTube 영상 한 개를 판매 종료 상태의 검수 강의에 등록한다. 가격·판매 상태·구매 권한은 그대로 유지한다.
2. 기존 결제 구매자의 내 강의실에서 '영상 준비 중'이 접근 링크로 바뀌는지 확인한다.
3. 링크를 열어 영상 제목과 실제 재생 여부를 확인한다. 단순 303 응답만으로 재생 성공으로 기록하지 않는다.
4. 비로그인 접근과 구매 권한 없는 계정의 접근은 차단되는지 확인한다. 공개 목록에 원본 영상 URL이 포함되지 않는지도 확인한다.
5. 추가 청구·결제 없이 기존 결제 권한으로 동작한 결과를 기록한다.

## 운영 전 확정할 내용

- 실제 판매할 강의명·가격·영상. 검수용 강의·계정·주문은 검수 데이터로 유지한다.
- 운영에 사용할 웹·신규 강의 DB·worker의 연결 대상. 기존 Sheets·학생 JSON·기존 관리자 인증·DATA_DIR·Volume을 보존한다.
- 운영 관리자 계정과 고객 문의·비밀번호 복구 연락 경로.
- 기존 운영 홈페이지 회귀 검수와 배포 결과·복구 절차 검토.
- Railway 실제 백업·복원 검증은 미완료다. Pro 자동 백업 도입은 사용자 결정으로 보류 상태다.

## 병합·배포 순서

2026-11-04 최신 fetch 기준 master f8749c969c30c903ad6bb0af99f015d635e898e2, 개발 코드 8189d4fd640de9aa6ed5123c4e2eedbfcfaf4b13이다. master 전용 추가 커밋은 없고 개발 브랜치가 6커밋 앞선다. git merge-tree로 내용 충돌이 없음을 확인했으며 실제 master 병합·push는 하지 않았다. 출시 직전에 다시 확인한다. 충돌 없음은 운영 설정과 DB 호환성 검수의 대체가 아니다.

1. master 최신 변경과 codex/lecture-service의 차이, 공통 의존성·잠금 파일·CI 파일 충돌을 검토한다. master 병합과 운영 배포는 별도 사용자 확인 후 진행한다.
2. 배포 직전 기존 운영 서비스의 소스·시작 명령·환경변수 이름·볼륨 연결 및 현재 정상 배포 버전을 기록한다. 비밀값은 문서/Git에 기록하지 않는다.
3. 신규 강의 DB의 상태·적용 대상·마이그레이션 체크섬을 확인한다. 기존 운영 Sheets나 학생 파일을 DB 초기화 대상으로 사용하지 않는다.
4. 새 배포의 마이그레이션·스키마 검사 후 웹을 준비한다. worker는 처음 SEND_ENABLED=false, --check로 인증·DB 연결을 확인한다.
5. 운영 Origin·로그인·기존 페이지·관리자·강의실을 검수하고, 실제 판매 항목과 수신자 안내를 확인한 후 발송을 활성화한다. 별도 검증 환경과 운영에서 동시에 같은 주문을 처리하지 않는다.
6. 미납 조회·실결제 반영·관리자 수동 대응을 확인하고 결과와 배포 버전을 기록한다.

## 장애 시 대응

- 발송 결과가 불명확하면 새 청구서를 만들거나 강제 재발송하지 않는다. worker 발송을 끄고 결제선생 내역·고정 청구 ID·금액을 확인한다.
- 결제선생 확인 후 관리자가 해당 주문만 수동 오픈·회수한다. 실제 환불/청구 파기는 결제선생에서 별도 처리한다.
- 웹 배포를 되돌리기 전 worker를 중지하고 진행 중 작업을 확인한다. 호환되지 않는 이전 웹과 새 DB를 혼합 실행하지 않는다. 적용된 SQL을 임의로 되돌리거나 결제 이력을 삭제하지 않는다.
- 기존 홈페이지 장애는 기록한 정상 배포와 환경·볼륨 연결을 기준으로 복구한다. 신규 기능의 문제 해결을 위해 기존 Sheets·학생 파일을 삭제/교체하지 않는다.

UI 동선 개선과 기존 데이터 전체 DB 이전, 설문·분류·추천, 실제 환불 API는 이번 기능 마무리 범위에 추가하지 않는다.
