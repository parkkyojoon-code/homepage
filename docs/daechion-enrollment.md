# 신규 상품 대치온 자동 등록

## 운영 범위

기존 홈페이지의 상품 추가 기능에 설명 없는 `프로세스1`/`프로세스2` 단일 선택 체크박스를 추가한다. 기본값과 선택값 없는 과거 데이터는 프로세스1이다. 새 상품도 프로세스1로 만들 수 있으며 생성 시각만으로 자동화하지 않는다. 기존 두 상품 `12course`, `chuweol`은 이후 결제도 프로세스1을 유지한다.

프로세스1은 기존 신청/Sheets/청구/장기 관리 안내/실장님 수동 등록 절차다. 프로세스2만 신규 DB/별도 Sheets/대치온 자동 등록/짧은 LMS 안내 절차다. 프로세스2에도 명시적인 상품 ID → 대치온 강의 ID 연결이 필요하다. 관리자 선택값은 서버에 저장하며 브라우저 신청 요청의 값으로 프로세스를 바꾸지 않는다.

현재 프로세스2 전용 최소 신청 화면과 /api/daechion/applications 접수를 연결했다. DAECHION_INTAKE_ENABLED는 기본 false이며, 서버 상품 연결·원본 DB·허용 origin 설정이 준비되지 않으면 접수하지 않는다. 웹 설정은 workers/daechion/web-env.example을 따른다. 기존 /api/apply는 프로세스2를 계속 차단하므로 프로세스1의 Sheets/안내 경로로 넘기지 않는다.

신규 흐름: 최소 신청 정보 → 기존 청구 담당 프로그램의 청구서 발송 → 결제선생의 실제 청구 ID/금액 대조 → 대치온 학생 조회/생성 → 강의 등록 → 간단한 LMS 준비 완료 안내.

- 자체 회원·강의실·학생카드·디스코드·기존 장기 과정 노션 안내를 추가하지 않는다.
- 학생 이름/학생 번호/청구 수신 번호/상품을 필수로 받는다. 보호자 로그인 번호는 선택이며 청구 수신 번호와 별개다.
- 비활성 학생도 실제 결제가 확인되면 등록하며 대치온의 자동 활성화를 허용한다.
- 자료·영상 권한은 대치온 전체 설정을 따른다. 학생별 기간·권한 API는 요구하지 않는다.
- 미래 차시, 환불 후 권한 회수, 시험 종료 시 강의 일괄 종료는 대치온에서 수동 처리한다.
- 미납은 발송 후 7일 대기 종료. 기한 후 결제는 관리자 확인하며 청구서를 자동 파기하지 않는다.
- 기존 계정의 비밀번호를 바꾸지 않는다. 새 계정에는 대치온 API 기본 초기 인증 규칙을 사용하고 비밀번호는 저장하지 않는다.

## 저장과 Sheets

사용자 결정: 신규 상품 신청·결제·등록 상태의 원본은 DB다. 실장님은 자동 반영된 Sheets 업무 목록으로 조회하고 재시도/보류 같은 조치는 기존 관리자 경계 안에서 처리한다. 기존 상품의 Sheets 운영은 유지한다.

확인한 기존 `수업 신청` 헤더는 A 시각, B 신청자 유형, C 이름, D 보호자 연락처, E 학생 연락처, F 출생년도, G~J 수업/과목 구분, K~L 확인/동의, M 결제 상태, N 문자 발송, O 청구서 발송, P 청구서 ID, Q Column 1, R 가격조정, S 청구 금액이다. 확인 범위 T/U의 헤더는 비어 있다. 학생 데이터 행은 읽거나 수정하지 않았다.

사용자 추가 결정: 신규 업무 목록은 기존 파일의 새 탭이 아니라 **별도 Google Sheets 파일**에 둔다. 기존 파일을 대상으로 설정하면 거부한다. 기존 시트 열은 재배치하지 않는다. 기존 청구 프로그램의 신규 상품 연결부는 DB의 신청/청구 식별자를 기준으로 처리해야 하며, 사람이 보는 Sheets를 수정해도 금융/수강 상태를 자동 변경한 것으로 취급하지 않는다. 구체적인 청구 큐 연결과 실제 새 업무 목록 생성/동기화 작업자는 아직 미구현이다.

업무 목록에는 학생 이름·선택 입력 학부모 이름·학생 번호·보호자 로그인 번호·청구 수신 번호, 상품/옵션/수업 방식, 금액 구성, 동의/추가 입력, 현재와 전체 청구서 번호, 결제/등록/안내 상태, 확인 사유와 마지막 갱신시각을 표시한다. 전화번호와 긴 청구서 ID는 문자열, 금액은 숫자로 유지한다. 쓰기는 RAW 값만 사용하고 직원용 메모 열은 동기화 범위 밖에 둔다. 직원이 정렬해도 신청 ID로 찾아 갱신해야 하므로 저장된 행 번호만 믿지 않는다.

## 현재 구현

- `lib/daechion/client.ts`: 실제 관리자 명세의 고정 HTTPS origin과 X-Api-Key 인증, 학생/강의 조회, 학생 생성, 차시 전체 수강 등록, 오류/응답 검사. fetch 주입 가능.
- `identity.ts`: 정확한 학생 번호/이름 확인, 비활성 계정 재사용, 409 중복 학생 재조회, 보호자 연결 충돌 검토. 결제 수신 번호는 이 모듈에 전달하지 않는다.
- `product-policy.ts`: 기존 두 상품 제외 우선, 명시적 유효 상품 연결만 허용.
- `purchase-process.ts`: 기본 프로세스1, 유효한 단일 값만 허용, 기존 두 상품 보호. 프로세스1은 대치온 연결 설정이 있어도 신규 자동화 원장에 접수하지 않는다.
- 요청이 시간 초과하면 POST를 무조건 반복하지 않는다. worker/원장은 결과 불명 상태를 기록하고 조회 후 복구해야 한다.
- 실제 API 오류 본문/개인정보/키를 오류 객체에 보관하지 않는다. upstream 메시지를 관리자나 로그에 그대로 전달하지 않는다.
- 실서비스 경로, 배치, DB, 청구서, 문자에는 아직 연결하지 않았다. 코드 import 자체로 네트워크 요청을 하지 않는다.
- `db/daechion/001_initial.sql`과 `scripts/daechion-migrations.cjs`: 별도 schema의 신청·청구·등록·outbox·이벤트 원장, 체크섬 이력, 트랜잭션/잠금 기반 적용. 아직 운영 DB에 적용하지 않았다.
- `ledger.ts`: 서버가 확정한 상품·가격 스냅샷으로 신청을 기록하고, 동일 요청 재전송/내용 충돌을 구분한다. 신청·등록 대상·Sheets 작업은 같은 트랜잭션으로 저장한다. 실제 청구 전에 숫자 bill_id를 예약하고 금액/중복 제약을 확인한다. 이 함수가 청구서를 보내지는 않는다.
- `intake.ts`: 프로세스2 전용 내부 접수 서비스. 학생/학부모 이름과 학생 번호·보호자 로그인 번호·청구 수신 번호를 구분하고, 공개 상품 여부·서버 저장 프로세스·수업 방식/캠퍼스·명시적인 대치온 연결을 검사한다. 가격은 서버 상품으로 계산하고 화면 금액과 다르면 저장 전에 거부한다. 브라우저의 가격/결제 상태/수강 대상 주입은 허용하지 않는다. 저장 성공은 `RECEIVED`로 반환하며 청구나 결제 완료를 의미하지 않는다. 재전송에는 같은 requestKey를 유지해야 한다. 비동기 발송 후 재전송될 수 있으므로 접수 응답에서 현재 청구 상태를 임의로 미발송이라고 표시하지 않는다.
- 상품 전체에 대한 강의 연결만 정의된 현재 단계에서는 과목 선택형 상품을 프로세스2로 접수하지 않는다. 선택한 과목과 대치온 강의의 대응을 구현하기 전까지, 일부 금액을 받고 전체 강의 권한을 부여하는 것을 방지한다. 프로세스1의 기존 과목 선택형 상품에는 영향이 없다.
- `database.ts`: DAECHION_DATABASE_URL 전용 지연 초기화 풀과 전용 연결 반환. 기존 LECTURES_DATABASE_URL이나 DATABASE_URL을 대신 사용하지 않는다. 공개 접수 라우트/화면은 아직 활성화하지 않았고, 기존 준비 중 응답을 유지한다. 먼저 청구 작업과 복구 경로를 연결해야 한다.
- `sheets-view.ts`: 신청별 전체 업무 행과 별도 파일 목적지 검증. 실제 Google API 호출이나 파일 생성은 하지 않는다.
- `billing.ts` / `payssam.ts`: 기존 V1 발송 방식과 대조한 DB 청구 연결. 숫자 20자리 청구 ID 선예약, 원자적인 1회 발송 확보, POST 전 SEND_UNKNOWN 커밋, 정상 응답 대조 후 SENT/7일 대기 기록, 변경마다 Sheets 갱신 작업/이벤트를 기록한다. 불명 결과는 자동 재발송하지 않는다. 청구서 유효기간은 기존 30일을 유지하고 7일 등록 대기와 분리한다. 수동 HOLD와 검토 사유를 해제하지 않는다.
- `workers/daechion/billing.cjs`: 별도 실행 가능한 프로세스2 청구 작업자. 기본 비활성, 발송은 별도 명시 플래그가 필요하다. `--check`는 마이그레이션 이력과 테이블 읽기만 하며 외부 발송/조회는 하지 않는다. 아직 운영에 생성/활성화하지 않았다. 실행·복구 규칙은 `workers/daechion/README.md`를 따른다.
- `payment.ts`와 V1 `read`: 실제 조회의 청구 ID/계정/금액/승인 시각 대조, 이전 응답 덮어쓰기 방지, 확인된 미납만 7일 대기 종료, 기한 내 결제의 지연 확인과 늦은 결제 구분. 금액/시간/발송 결과 불명이나 취소는 수동 확인이다. 관리자의 HOLD/REVOKED를 자동 해제하지 않으며, 이미 확인한 승인 시각을 다른 값으로 덮어쓰지 않는다.
- `enrollment.ts`: 결제 확인된 신청의 등록 claim, 학생 조회/자동 생성, 대치온 강의 등록, 모든 대상 완료 후 READY_MESSAGE 1회 큐잉. 생성/등록 직전과 결과 기록 시 결제·보류·claim을 재검사한다. 만료/결과 불명 claim은 REVIEW이며 무조건 재시도하지 않는다. 실제 문자 전송은 아직 아니다.
- 작업자에 조회·등록 전용 기본 비활성 플래그를 추가했다. 실제 등록 실행 전 `/v1/me`의 tenant가 서버에 설정한 기대 tenant와 일치해야 한다. `--check`는 이 외부 API조차 호출하지 않는다. 운영 tenant 값/실제 키를 이용한 검수는 아직 하지 않았다.

## 검증

`npm run test:daechion`은 TypeScript, 모의 HTTP 계약, 로컬 PGlite의 SQL/원장·Sheets 투영 검사를 수행한다. 실제 자격 증명, 외부 API나 학생 데이터가 필요하지 않다. GitHub에서는 격리된 PostgreSQL 18 서비스로 마이그레이션 잠금과 동시 신청 재전송도 검사한다. 실제 운영 DB에 대한 검사가 아니다.

DB 작업 명령은 `npm run db:daechion:status`, `npm run db:daechion:check`, `npm run db:daechion:migrate -- --database NAME`이다. DAECHION_DATABASE_URL을 별도로 설정하고 적용 시 실제 DB 이름과 일치해야 한다. 기존 LECTURES_* 설정/기록을 재사용하거나 기존 홈페이지 배포에 이 명령을 자동 추가하지 않는다.

## 다음 구현 단위

### 기존·신규 이중 확인 보완

프로세스2 신청은 studentHistory=EXISTING/NEW 단일 선택이 필수다. 기본값은 없고, 선택값 없는 과거 기록은 수동 확인이다. StudentHistoryChoice 체크박스를 전용 신청 화면에 연결했다. 기존 프로세스1 화면에는 추가하지 않는다.

학생 번호와 보호자 로그인 번호 모두 이름 필터 없이 조회하고 대치온 학생 ID로 합친다. 어느 번호든 기존 기록이 있으면 기존으로 분류한다. 신청 선택과 다른 결과, 이름/역할/보호자 연결 불일치, 형제자매 등 복수 후보, 조회 실패는 자동 생성·등록·완료 안내를 보류한다. 결제 번호는 조회 근거가 아니다. 신규 생성 중 409도 조용히 기존 계정으로 대체하지 않는다.

002_identity.sql은 검증 상태/확정 계정/자체 생성 근거와 번호별 생성 확보를 별도 테이블에 저장한다. 001 파일/기존 신청 스냅샷은 바꾸지 않는다. 마이그레이션 실행기는 체크섬이 검증된 이력의 뒤에만 새 파일을 적용한다. 같은 신청의 여러 강의는 자체 생성 근거를 재사용하지만 다른 신청에서 생긴 계정은 선택 불일치로 확인한다. 외부 생성 결과가 불명인 번호 확보는 자동 해제하지 않는다.

Sheets 투영에 기존·신규 선택/전화번호 대조 결과/중복 수강생 확인/중복 확인 사유를 추가했다. 통과는 초록색, 확인 필요는 빨간색·흰색 굵은 글씨, 조회 대기는 회색 조건부 서식이다. 아직 실제 Sheets 발행기에 연결하거나 새 파일을 생성하지 않았다. 선택값 누락은 빨간색 확인 필요이며 근거 없는 통과 표시도 거부한다. 실장님이 확인할 수동 처리 화면/감사 이력은 후속 연결이다.

실제 API에서 학생·학부모 1/2 번호와 비활성 학생 조회 범위를 검수하기 전에는 DAECHION_IDENTITY_LOOKUP_VERIFIED를 true로 설정하지 않는다. 등록 작업자도 이 설정 없이는 실행하지 않는다. 실제 검수는 아직 진행하지 않았다.

1. 원장과 결제 조회·등록 작업 확보·완료 안내 큐까지 연결했다. 실제 안내 문자 전송·관리자 복구 화면·Sheets 동기화와 운영 검수는 남아 있다. 기본 원장과 마이그레이션은 운영에 아직 활성화하지 않았다.
2. 기존 청구 방식의 새 상품 전용 연결부와 실행 작업자는 준비했다. 콜백 경로와 운영 비공개 설정을 연결한 뒤 검수한다. 기존 register_checker 프로그램은 수정하지 않는다.
3. 프로세스2 전용 신청 화면과 DB 접수를 연결한다. 실패를 완료로 표시하지 않는 처리는 프로세스2에 적용한다. 기존 프로세스1의 화면/동작을 이 작업으로 전역 수정하지 않는다.
4. Sheets 업무 목록과 관리자 처리 수단.
5. 실제 키의 tenant/scopes 읽기 전용 검사, 승인된 학생/강의 시험, 운영 적용.

## 전용 신청과 Sheets 발행 연결

신청 화면은 학생/학부모 이름, 학생 번호, 보호자 로그인 번호, 청구 수신 번호, 기존·신규와 신청자 선택, 금액/동의를 받는다. 과거 장기 과정의 학생카드/Discord/Notion 안내를 넣지 않는다. 응답 오류를 접수 완료로 표시하지 않으며 불명 응답은 동일 UUID/내용으로 다시 확인한다. UUID만 sessionStorage에 보관하고 이름/전화번호는 저장하지 않는다. 미확정 시 입력을 잠가 다른 내용으로 같은 신청을 재생하지 않는다.

공개 접수는 허용 origin, JSON/8KiB 한도, 필수 선택과 서버 상품/가격 검증 후 DB에 저장한다. 접수 완료는 결제/발송 완료가 아니다. UUID 재전송은 동일 신청으로 처리하고, 다른 UUID의 같은 학생·상품 5분 내 중복과 동일 결제 번호의 15분 내 10건 초과 접수는 DB 트랜잭션/잠금으로 제한한다. 기존 프로세스1에는 적용하지 않는다. 운영 활성화 전 전체 발송/관리자 복구 경로를 검수해야 한다.

Sheets 발행은 DAECHION_SHEETS_ENABLED 기본 false다. 원본 DB를 조회해 전체 업무 행을 만들고, 별도 파일/탭만 대상으로 한다. 기존 파일 ID를 거부하고 초기화 표식·헤더를 확인한다. --setup-sheets는 명시적 실행일 때만 빈 새 탭의 헤더/직원 메모 열/중복 확인 색상을 초기화한다. 데이터가 있으면 덮어쓰지 않는다. 실제 파일은 아직 만들거나 수정하지 않았다.

신청 UUID를 행 developer metadata로 묶고 기존 행은 metadata ID 기반 RAW 갱신을 한다. 신규 행 삽입·문자열/숫자 값·UUID 표식은 한 batchUpdate로 생성한다. 전화번호/긴 청구 ID/수식처럼 보이는 이름은 문자열이며 직원 메모 열은 쓰지 않는다. 헤더 변경/중복 표식은 확인 대상으로 남긴다. Google 명세: https://developers.google.com/workspace/sheets/api/guides/metadata 및 https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets.values/batchUpdateByDataFilter . 실제 정렬/메모 보존은 별도 파일 검수에서도 확인한다.

SHEETS outbox는 신청 단위로 한 작업자만 확보하고 최신 DB 버전까지 이전 작업을 합친다. 쓰기 결과 불명/만료는 UNKNOWN으로 남겨 같은 신청의 후속 삽입을 막는다. Google 장애가 금융·대치온 등록 상태를 변경하지 않는다. 실제 안내 문자 전송, 관리자 처리 화면, 실제 새 Sheets 생성/공유·초기화/정렬 검수와 운영 설정은 남아 있다.

현재 키 유효성/scopes와 실제 API 동작은 아직 미검증이다. 상품 정보도 미정이다. 실제 키를 Git/일반 문서/로그에 넣지 않는다. 실제 학생 생성과 수강 등록, 메시지 발송, 운영 DB 재가동은 별도 연결/검수 단계다. 종료한 자체 `/lectures` 시스템과 그 인증을 재사용하거나 다시 열지 않는다.

## 관리자 확인과 LMS 안내 연결 (2026-11-06)

앞 절의 후속 항목 중 관리자 화면/API와 안내 문자 실행기를 개발 브랜치에 구현했다. `/admin/daechion`은 기존 관리자 로그인으로 신청 검색, 확인 필요 목록, 제출 정보·청구 번호·강의별 등록·발송 접수·처리 이력을 조회한다. `DAECHION_ADMIN_ENABLED`는 기본 false이고 API는 관리자 쿠키, 허용 origin, 요청 크기를 검증한다. 자체 회원 시스템을 다시 열지 않는다.

관리자는 자동 처리 보류, 학생 확인 후 자동 등록 재개, 결제선생 수동 확인 기록, 대치온 수동 등록/회수 완료 기록을 남길 수 있다. 수동 완료/회수는 외부 사이트에서 직접 마친 작업의 기록이며 실제 권한 변경/환불 API를 호출하지 않는다. 자동 등록 재개는 결제와 기한을 확인하고, 대치온 학생 ID·이름·학생 번호·보호자 연결을 다시 검증한다. 기존·신규 원래 선택은 수정하지 않고 수동 확인 근거를 별도로 남긴다. 늦은 결제처럼 자동 재개 조건에 맞지 않으면 외부에서 처리한 뒤 완료를 기록한다.

`003_admin_messages.sql`은 담당자·사유·근거를 저장하는 감사 이력과 수신 번호별 발송 접수 원장을 추가한다. 요청 UUID와 신청 버전으로 중복 저장/오래된 화면의 덮어쓰기를 차단한다. 현재 기존 관리자 로그인은 공용 인증이므로 담당자 이름은 직접 입력한 기록이며 개인별 인증된 직원 신원으로 간주하지 않는다.

LMS 안내는 결제 확인·본인 확인·모든 연결 강의의 등록 완료 후에만 큐에 넣는다. 수신자는 학생 번호와 선택한 보호자 로그인 번호이며 동일 번호는 한 번만 보낸다. 결제 번호에는 별도 로그인 안내를 보내지 않는다. 대치온 링크와 기존 비밀번호 유지/처음 생성된 계정의 초기 비밀번호 안내만 포함하고 학생카드·Discord·Notion은 넣지 않는다. 기존 계정 비밀번호를 변경하거나 실제 비밀번호를 DB/로그에 저장하지 않는다.

`DAECHION_READY_MESSAGE_ENABLED`는 기본 false다. 별도 솔라피 설정을 사용하고 외부 호출 전에 수신 번호별 상태를 UNKNOWN으로 저장한다. 제공자가 해당 영수증 UUID의 발송 접수를 확인한 경우에만 SENT로 바꾼다. SENT는 발송 접수이며 실제 휴대전화 도착 보장은 아니다. 일부 성공 후 응답 불명, 작업 시간 초과, 중간 보류는 자동 재발송하지 않는다. 이미 접수된 수신자에게도 중복 발송하지 않는다. `--check`는 발송 플래그를 켜도 외부 호출을 하지 않는다. 공식 명세: https://solapi.com/developers/api/messages 및 https://solapi.com/developers/api/messages-lms .

화면은 가상 신청 1건과 읽기 전용 로컬 API로 검수했다. 실제 관리자 저장 동작은 DB 테스트로 별도 검증한다. 운영 DB 마이그레이션, 실제 키/번호 조회 범위 확인, 새 Sheets 생성·공유·정렬 검수, 실제 문자/등록 검수, 관리자 상품과 대치온 강의 연결 설정은 남아 있다. 현재 운영 홈페이지·기존 Sheets·기존 작업자는 바꾸지 않았다.

## 관리자 상품과 고유 강의 ID 연결 (2026-11-06)

관리자 수업 추가/수정에서 프로세스2를 선택하면 연결할 대치온 강의 항목이 나타난다. 목록 불러오기는 기존 관리자 인증 후 서버에서 `/v1/me`의 tenant를 확인하고 `/v1/lectures`를 조회한다. 화면에는 강의명·고유 ID·차시 수를 함께 표시하며 이름이 같은 강의도 ID별로 선택한다. 종료되거나 차시가 없는 강의는 선택하지 못한다. 외부 링크의 주소 구조를 추정하지 않으며 링크 입력은 제공하지 않는다. API 키는 서버 비공개 설정에만 둔다.

관리자는 최대 30개 ID를 명시적으로 연결할 수 있다. 하나의 판매 상품이 여러 강의로 구성된 경우 선택한 모든 강의에 등록한다. 저장 때 서버가 목록과 tenant를 다시 조회해 존재·개설·차시 유무를 검증한다. 브라우저가 보낸 강의명/tenant/검증 일시는 신뢰하지 않는다. 같은 ID가 여러 번 나오거나 다른 tenant의 키, 없는 ID, 종료/빈 강의면 저장을 거부한다. 검증 도중 다른 상품 수정은 보존하고 같은 상품의 변경은 충돌로 처리한다. 편집 화면이 알고 있는 기존 연결의 검증 시각을 비교해 오래된 화면의 연결 덮어쓰기를 거부한다. 이미지 업로드 등 연결 외 수정만으로 이 비교를 무효화하지 않는다.

연결 설정은 기존 상품 관리가 사용하는 Volume의 classes.json에 `daechionBinding`으로 저장한다. API로 확인한 tenant ID·강의 ID/표시명·확인 시각을 기록한다. 신규 신청 시 이 서버 설정에서 등록 대상을 결정하고 기존 DB의 registrations에 복사하며 tenant도 불변 신청 스냅샷에 넣는다. 신청 후 상품 연결을 바꿔도 이미 접수된 신청의 등록 대상은 바뀌지 않는다. 다른 tenant로 작업자가 바뀌면 신규 스냅샷의 학생 생성/등록을 보류하며, 관리자 수동 등록 완료·재개도 tenant가 일치해야 한다.

기존 DAECHION_PRODUCT_BINDINGS_JSON은 관리자 설정이 없는 상품만을 위한 호환 설정이다. 관리자에서 연결 해제 후 저장하면 null 표식을 남겨 환경변수로 우회 재연결되지 않는다. 연결 없는 프로세스2 상품은 초안으로 저장할 수 있지만 신청 접수는 불가하다. 프로세스1과 원래 두 상품에는 대치온 연결을 적용하지 않는다. 상품별 연결을 위해 새 환경변수를 추가할 필요가 없다.

같은 이름의 가상 강의 두 개 중 ID 102만 선택되는 화면을 읽기 전용 로컬 API로 검수했다. 실제 키의 목록과 저장·신청·결제·등록 검수는 아직 남아 있다. 새 기능의 단위/DB/HTTP 검사와 제품 빌드를 수행했다. 프로젝트 전체 tsc 검사는 기존 중복 스타일 속성, 기존 ClassMode 필수 campuses 누락, ES2020 미만 target의 BigInt 등 기존 오류가 있어 통과 상태가 아니다. 대치온 전용 TypeScript 빌드는 별도 검증하며 전역 검사 결과는 로컬 outputs/daechion-binding-types-20261106.txt에 기록한다.
