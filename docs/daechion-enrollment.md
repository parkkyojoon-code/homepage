# 신규 상품 대치온 자동 등록

## 운영 범위

기존 홈페이지의 상품 추가 기능을 유지한다. 기존 두 상품 `12course`, `chuweol`은 이후 결제도 자동 등록에서 제외한다. 새 상품이라도 명시적인 상품 ID → 대치온 강의 ID 연결이 없으면 처리하지 않는다.

신규 흐름: 최소 신청 정보 → 기존 청구 담당 프로그램의 청구서 발송 → 결제선생의 실제 청구 ID/금액 대조 → 대치온 학생 조회/생성 → 강의 등록 → 간단한 LMS 준비 완료 안내.

- 자체 회원·강의실·학생카드·디스코드·기존 장기 과정 노션 안내를 추가하지 않는다.
- 학생 이름/학생 번호/청구 수신 번호/상품을 필수로 받는다. 보호자 로그인 번호는 선택이며 청구 수신 번호와 별개다.
- 비활성 학생도 실제 결제가 확인되면 등록하며 대치온의 자동 활성화를 허용한다.
- 자료·영상 권한은 대치온 전체 설정을 따른다. 학생별 기간·권한 API는 요구하지 않는다.
- 미래 차시, 환불 후 권한 회수, 시험 종료 시 강의 일괄 종료는 대치온에서 수동 처리한다.
- 미납은 발송 후 7일 대기 종료. 기한 후 결제는 관리자 확인하며 청구서를 자동 파기하지 않는다.
- 기존 계정의 비밀번호를 바꾸지 않는다. 새 계정에는 대치온 API 기본 초기 인증 규칙을 사용하고 비밀번호는 저장하지 않는다.

## 저장과 Sheets

사용자 결정: 신규 상품 신청·결제·등록 상태의 원본은 DB다. 실장님은 자동 반영된 Sheets 업무 목록으로 조회하고 재시도/보류 같은 조치는 기존 관리자 경계 안에서 처리한다. 기존 상품의 Sheets 운영은 유지한다.

확인한 기존 `수업 신청` 헤더는 A 시각, B 신청자 유형, C 이름, D 보호자 연락처, E 학생 연락처, F 출생년도, G~J 수업/과목 구분, K~L 확인/동의, M 결제 상태, N 문자 발송, O 청구서 발송, P 청구서 ID, Q Column 1, R 가격조정, S 청구 금액이다. 확인 범위 T/U의 헤더는 비어 있다. 학생 데이터 행은 읽거나 수정하지 않았다.

사용자 추가 결정: 신규 업무 목록은 기존 파일의 새 탭이 아니라 **별도 Google Sheets 파일**에 둔다. 기존 파일을 대상으로 설정하면 거부한다. 기존 시트 열은 재배치하지 않는다. 기존 청구 프로그램의 신규 상품 연결부는 DB의 신청/청구 식별자를 기준으로 처리해야 하며, 사람이 보는 Sheets를 수정해도 금융/수강 상태를 자동 변경한 것으로 취급하지 않는다. 구체적인 청구 큐 연결과 실제 새 업무 목록 생성/동기화 작업자는 아직 미구현이다.

업무 목록에는 학생 이름·선택 입력 학부모 이름·학생 번호·보호자 로그인 번호·청구 수신 번호, 상품/옵션/수업 방식, 금액 구성, 동의/추가 입력, 현재와 전체 청구서 번호, 결제/등록/안내 상태, 확인 사유와 마지막 갱신시각을 표시한다. 전화번호와 긴 청구서 ID는 문자열, 금액은 숫자로 유지한다. 쓰기는 RAW 값만 사용하고 직원용 메모 열은 동기화 범위 밖에 둔다. 직원이 정렬해도 신청 ID로 찾아 갱신해야 하므로 저장된 행 번호만 믿지 않는다.

## 현재 구현

- `lib/daechion/client.ts`: 실제 관리자 명세의 고정 HTTPS origin과 X-Api-Key 인증, 학생/강의 조회, 학생 생성, 차시 전체 수강 등록, 오류/응답 검사. fetch 주입 가능.
- `identity.ts`: 정확한 학생 번호/이름 확인, 비활성 계정 재사용, 409 중복 학생 재조회, 보호자 연결 충돌 검토. 결제 수신 번호는 이 모듈에 전달하지 않는다.
- `product-policy.ts`: 기존 두 상품 제외 우선, 명시적 유효 상품 연결만 허용.
- 요청이 시간 초과하면 POST를 무조건 반복하지 않는다. worker/원장은 결과 불명 상태를 기록하고 조회 후 복구해야 한다.
- 실제 API 오류 본문/개인정보/키를 오류 객체에 보관하지 않는다. upstream 메시지를 관리자나 로그에 그대로 전달하지 않는다.
- 실서비스 경로, 배치, DB, 청구서, 문자에는 아직 연결하지 않았다. 코드 import 자체로 네트워크 요청을 하지 않는다.
- `db/daechion/001_initial.sql`과 `scripts/daechion-migrations.cjs`: 별도 schema의 신청·청구·등록·outbox·이벤트 원장, 체크섬 이력, 트랜잭션/잠금 기반 적용. 아직 운영 DB에 적용하지 않았다.
- `ledger.ts`: 서버가 확정한 상품·가격 스냅샷으로 신청을 기록하고, 동일 요청 재전송/내용 충돌을 구분한다. 신청·등록 대상·Sheets 작업은 같은 트랜잭션으로 저장한다. 실제 청구 전에 숫자 bill_id를 예약하고 금액/중복 제약을 확인한다. 이 함수가 청구서를 보내지는 않는다.
- `sheets-view.ts`: 신청별 전체 업무 행과 별도 파일 목적지 검증. 실제 Google API 호출이나 파일 생성은 하지 않는다.

## 검증

`npm run test:daechion`은 TypeScript, 모의 HTTP 계약, 로컬 PGlite의 SQL/원장·Sheets 투영 검사를 수행한다. 실제 자격 증명, 외부 API나 학생 데이터가 필요하지 않다. GitHub에서는 격리된 PostgreSQL 18 서비스로 마이그레이션 잠금과 동시 신청 재전송도 검사한다. 실제 운영 DB에 대한 검사가 아니다.

DB 작업 명령은 `npm run db:daechion:status`, `npm run db:daechion:check`, `npm run db:daechion:migrate -- --database NAME`이다. DAECHION_DATABASE_URL을 별도로 설정하고 적용 시 실제 DB 이름과 일치해야 한다. 기존 LECTURES_* 설정/기록을 재사용하거나 기존 홈페이지 배포에 이 명령을 자동 추가하지 않는다.

## 다음 구현 단위

1. 원장/스키마에 실제 결제 증거·등록 작업 확보/재시도·안내 발송 순서를 연결한다. 기본 원장과 마이그레이션은 준비됐으며 아직 활성화하지 않았다.
2. 기존 청구 담당 프로그램의 새 상품용 연결부. 새 자동화 worker에서 청구서를 중복 발송하지 않는다.
3. 신규 신청 분기 및 오류 시 무조건 완료를 표시하는 기존 화면의 접수 처리 수정.
4. Sheets 업무 목록과 관리자 처리 수단.
5. 실제 키의 tenant/scopes 읽기 전용 검사, 승인된 학생/강의 시험, 운영 적용.

현재 키 유효성/scopes와 실제 API 동작은 아직 미검증이다. 상품 정보도 미정이다. 실제 키를 Git/일반 문서/로그에 넣지 않는다. 실제 학생 생성과 수강 등록, 메시지 발송, 운영 DB 재가동은 별도 연결/검수 단계다. 종료한 자체 `/lectures` 시스템과 그 인증을 재사용하거나 다시 열지 않는다.
