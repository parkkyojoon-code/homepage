# Sheets에서 오류 확인

신규 강의 전용 업무 파일만 사용한다. 별도 문자·이메일·메신저 알림은 보내지 않는다.

## 담당자 확인

- 기존 신청 목록의 `확인 필요 사유`에 신청별 `오류 확인 필요: 실패 단계`가 표시된다. 오류가 남은 셀은 빨간색이다. 기존 업무 열·직원 메모·중복 수강생 판정은 유지한다.
- 같은 파일의 `자동화 점검` 탭에서 빨간 `확인 필요` 행을 확인한다. 신청번호로 원래 목록의 학생·상품·청구서 정보를 찾는다. 인증 오류처럼 신청 한 건에 속하지 않는 문제는 `공통 작업자`로 표시한다.
- 단계·오류 구분·누적 발생 횟수·최초/최근 발생시각·복구 확인시각을 한국시간으로 표시한다. 동일 범위/단계의 반복 오류는 한 행으로 묶는다. 실제 해당 작업 성공 확인 후 `복구 확인`으로 바뀐다. 단순 재실행이나 건너뛰기는 복구가 아니다.
- 결과 불명(UNKNOWN)은 담당자가 공급자 내역을 확인한다. 이 기능은 청구·문자·수강 등록을 다시 실행하거나 상태를 강제로 성공 처리하지 않는다. 기존 수동 확인/복구 절차를 사용한다.
- `자동화 점검`은 자동 갱신 영역이다. 메모는 원래 신청 목록의 직원 메모 열에 쓴다.

## 표시 지연과 한계

일반 운영은 각 작업 주기 후 반영한다(기본 주기 30초에 실제 처리 시간이 추가됨). 인증 유지 전용 모드는 인증 점검 후 반영한다(성공 시 15분, 실패 시 1분 간격에 실제 처리 시간이 추가됨). 이는 서버 처리 기록이며 학생 단말의 수신·시청 성공을 대신하지 않는다.

Sheets 연결 장애 중에는 그 시트에 즉시 오류를 쓸 수 없다. DB에 저장된 실패와 결과 불명 작업은 연결 복구 후 반영한다. DB 기록 자체가 실패했으면 보존을 보장할 수 없으며, 현재 프로세스가 인지한 기록 저장 실패를 점검 탭에 표시한다. 프로세스 종료/서버 중단 중에는 시트 갱신도 멈춘다. 따라서 상단 `마지막 실행·시트 반영 확인`이 30분 이상 오래됐으면 Railway 실행·DB·Sheets 연결을 확인한다. 이 시간은 별도 외부 감시나 휴대전화 알림이 아니다.

과거 `failed: 1`의 단계를 새로 추정해 입력하지 않는다. 보완 배포 이후 포착한 오류와 현재 DB의 결과 불명 상태를 표시한다.

## 운영 반영

1. 기존 자동화 스키마의 `006_operations.sql`을 적용한다. 기존 데이터·스키마를 삭제하거나 이전하지 않는다.
2. 웹/작업자의 마이그레이션 목록을 같은 버전으로 배포한다. 이미 가동 중인 이전 코드의 스키마 검사와 신규 이력이 불일치하지 않도록 순서를 조율한다.
3. 작업자에 `DAECHION_DIAGNOSTICS_SHEETS_ENABLED=true`를 설정한다. 기존 신규 파일 ID·탭 ID·서비스 계정을 재사용한다. 새 공유 권한이나 인증 키를 만들지 않는다.
4. 초기 실행이 전용 파일에 메타데이터가 있는 신청 탭을 확인한 뒤 `자동화 점검` 탭을 생성한다. 같은 이름의 다른 탭이 있으면 덮어쓰지 않고 중단한다. 기존 학생 Sheets는 거부한다.
5. 실제 오류를 만들기 위해 청구·등록을 실행하지 않는다. 격리 DB/Sheets API 테스트로 실패/복구와 보존 동작을 검증하고, 운영에서는 인증 유지·점검 시트 반영만 확인한다.

점검 기능은 금융 스위치와 독립적이다. `--session-only`에서도 오류·상태 시트 반영은 허용되지만 청구·결제 조회·학생 생성·권한 부여·문자는 실행하지 않는다. DB와 시트에는 허용된 고정 오류 코드만 저장하며 공급자 오류 본문·키·비밀번호·쿠키를 저장/출력하지 않는다.
